== Embeddings

Embedding models convert text, images, or other content into vectors that capture semantic meaning. In a RAG system, these vectors let the retriever search large unstructured collections for content that is relevant to a user's question. The retriever embeds the query, compares it to vectors stored in a vector database, and ranks candidates by distance. Smaller distances indicate higher semantic similarity, which determines what fits into the LLM's limited context window.

A typical embedding based retrieval flow looks like this:

. Split documents into chunks and embed them when building the vector database.
. Embed each incoming user query with the same model.
. Compute distances between the query vector and stored vectors.
. Retrieve the closest chunks and pass them to the LLM as context.

This chapter shows how to work with embedding models from providers such as OpenAI, Google, and open source projects. You will generate embeddings, visualize semantic relationships, measure vector distances, and use them in practical RAG pipelines. The recipes also cover model selection, multimodal embeddings, and hybrid retrieval that combines vectors with keyword or metadata filters.

You can find all the code examples for this chapter in the https://github.com/polzerdo55862/RAG-with-Python-Cookbook[book's GitHub repository].

To use them, you need to install the OpenAI SDK and the Sentence Transformers library:

[source,bash]
----

The following code snippet uses the OpenAI SDK and one of OpenAI's text embedding models to generate embedding vectors for two sample text strings.

[source, python, indent=0]
----
from openai import OpenAI

text_chunks = ["The sky is blue.", "The grass is green."]

client = OpenAI()  # uses the environment variable OPENAI_API_KEY

embeddings_list = []

for text_chunk in text_chunks:
    response = client.embeddings.create(
        input=[text_chunk], model="text-embedding-3-small"
    )
    embedding = response.data[0].embedding
    embeddings_list.append(embedding)
----

The `response` object returned by the OpenAI API contains a `data` attribute, which is a list of embedding objects. Each embedding object has an `embedding` attribute that holds the actual vector, a Python list of floating-point numbers. For the `text-embedding-3-small` model, this list contains 1,536 values. The embeddings are normalized, with individual values typically ranging between -1 and 1, though most fall within a narrower range. The code above extracts the first embedding from the response using `response.data[0].embedding`.

<<figure_how_embeddings_look>> shows what the list of embedding vectors looks like. Here the generated embeddings have 1,536 dimensions per vector.

As an alternative to OpenAI, you can use smaller open source models. The example below uses one of the most popular open source models, `all-MiniLM-L6-v2`. While the accuracy and performance is not comparable to modern transformer-based foundation embedding models from Google or OpenAI, it remains a popular choice because it is fast, cost-efficient, and can run on your own infrastructure, which allows you to even deploy it on smaller edge devices or your local laptop.

The code uses the Sentence Transformers library, which builds on Hugging Face Transformers and is specifically designed for generating text embeddings:

[source, python, indent=0]
----
from sentence_transformers import SentenceTransformer

# Load the model
model = SentenceTransformer("sentence-transformers/all-MiniLM-L6-v2")
text_chunks = ["The sky is blue.", "The grass is green."]

embeddings = model.encode(text_chunks)
----

The `encode` method returns a NumPy array where each row represents the embedding vector for the corresponding text chunk. The resulting `embeddings` array has shape (2, 384), meaning 2 text chunks with 384-dimensional vectors.

==== Discussion

Embedding models transform text into numerical vectors that capture semantic meaning. This is the core mechanism enabling RAG systems to find relevant content by measuring similarity in vector space rather than relying on exact keyword matches.

Modern text embedding models learn semantic relationships by training on large text datasets. Understanding how they differ from simpler encoding methods like one-hot encoding clarifies their power. One-hot encoding treats categories as independent labels with no semantic relationship, while embedding models learn meaningful representations where similar concepts are positioned close together in vector space.

<<image_one_hot_encoding>> shows one-hot encoding, which represents "Bachelor" as [0, 1, 0], "Master" as [1, 0, 0], and "PhD" as [0, 0, 1]. These randomly assigned vectors lose all semantic information. They do not capture that a PhD student typically has a Bachelor's degree first, or that these degrees represent different levels of education.

Shows label encoding assigning numbers for categories and one-hot encoding creating 3-dimensional binary vectors for the same categories]

[NOTE]
====
A vector is a list of numbers representing something in a structured way (like coordinates on a map where [5, 3] means "5 blocks north and 3 blocks east"). Vectors let us represent abstract concepts (like word meanings) as numbers that computers can work with and compare mathematically.
====

RAG systems depend on embedding models that capture semantic meaning because they enable retrieval based on conceptual relationships rather than just keyword matches. <<image_example_embeddings>> shows this with the royal titles example. Instead of random numbers, this creates vectors where each dimension has a clear meaning, mapping characteristics into vector space. The image maps the words queen, king, princess, and prince using three meaningful dimensions: age (kings are typically older than princes), gender (queens and princesses are female), and royal status (hierarchy levels in the royal family).

So a king might get the vector [0.8, 0, 1], which stands for an older male with high status. Each number represents a specific characteristic: age, gender, and royal status. A princess is represented as [0.3, 1, 0.5] (younger, female, lower status).

You can even perform arithmetic with these vectors. When you add or subtract vectors, you add or subtract each corresponding number:

----
king - man + woman = queen
[0.8, 0, 1] - [0.7, 0, 0.6] + [0.6, 1, 0.5]
= [0.8 - 0.7 + 0.6, 0 - 0 + 1, 1 - 0.6 + 0.5]
= [0.7, 1, 0.9]
----

This works because subtracting "man" and adding "woman" changes the gender dimension while preserving age and status, resulting in a vector that describes a queen.

<<image_example_embeddings>> visualizes this concept for the royal example and shows a second example using capitals and countries: Paris - France + Italy = Rome.

Embedding models are neural networks trained on large text datasets. Each unique word in the dataset is assigned to a neuron in the input layer. <<image_how_embedding_models_work>> shows a simple example with a hidden layer containing only two neurons. During training, the neural network predicts the next word for each input word. For example, when the input neuron for "Google" is activated, the network is trained to predict the word "is". Once the model is fully trained, the weights of the hidden layer neurons become the embedding model. These learned weights map every word or sentence into a space and determine each word's position.

[[image_how_embedding_models_work]]
.Neural Network Architecture for Generating Text Embeddings
image::img/ch05_images/how_vector_embedding_models_work.png[Simplified neural network diagram for embedding model. Shows input layer with neurons for vocabulary words, hidden layer with 2 neurons, and output predictions. Illustrates how word predictions determine embedding vector positions]

Use embedding models for any RAG system that needs to find relevant content based on semantic meaning rather than exact keyword matches. This includes question answering, document retrieval, and content recommendation systems.

Avoid embeddings when you need exact string matching (use full-text search), when dealing with highly structured data like database queries (use SQL), or when interpretability is critical (embeddings are black boxes). The main tradeoff is cost versus accuracy: cloud-based models like OpenAI's text-embedding-3-small offer better accuracy but incur API costs, while open-source models like all-MiniLM-L6-v2 run locally but with lower retrieval quality.

While their evolution has not been as dramatic as LLMs, embedding models remain fundamental to RAG systems. Most current models, even those from a few years ago, deliver strong performance, making the choice more about infrastructure constraints (cloud vs. local) than accuracy differences.

=== Visualizing Semantic Relationships Between Text Chunks Using Dimensionality Reduction Techniques

==== Problem

You want to visualize high-dimensional embedding vectors in two dimensions to verify that semantically similar text appears clustered together.

==== Solution

<<image_reducing_dimensionality>> shows the dimensionality reduction process. Use PCA (Principal Component Analysis) to reduce embedding dimensions from 1,536 to 2 and plot them with matplotlib. This reveals semantic patterns by showing which text chunks cluster together based on meaning.

[[image_reducing_dimensionality]]
.Dimensionality Reduction Process Using Principal Component Analysis
image::img/ch05_images/reducing_dimensionality.png[Process flow diagram showing dimensionality reduction using PCA. Input shows high-dimensional embedding vectors as vertical bars of varying heights representing multiple dimensions. Output shows compressed representation where tallest bars represent principal components capturing most information]

The code uses Principal Component Analysis (PCA) from scikit-learn, a popular machine learning library that provides tools for dimensionality reduction and data analysis. Matplotlib is used to create the visualization, and pandas helps manage the embedding data in tabular form.

To run the code, install the following dependencies.

[source,bash]
----
pip install openai scikit-learn matplotlib pandas
----

The following code generates embeddings for six example sentences and stores them together with the text chunks in a DataFrame.

[source, python, indent=0]
----
import os
import pandas as pd
import matplotlib.pyplot as plt
from sklearn.decomposition import PCA
from openai import OpenAI

# Define text chunks
text_chunks = [
    "The sky is blue.",
    "The sun is shining.",
    "I love chocolate.",
    "Ice cream is delicious.",
    "Roses are red.",
    "Violets are blue.",
]

# Initialize OpenAI client
# Assumes the OPENAI_API_KEY environment variable is set
client = OpenAI()
embeddings = []

# Generate embeddings for text chunks
for text_chunk in text_chunks:
    response = client.embeddings.create(
        input=[text_chunk], model="text-embedding-3-small"
    )
    embeddings.append(response.data[0].embedding)

# Convert embeddings to a DataFrame
# Each row represents one text chunk, each column one embedding dimension
embeddings_df = pd.DataFrame(
    embeddings, columns=[f"dim_{i}" for i in range(len(embeddings[0]))]
)
----

Next, the PCA function from scikit-learn transforms the embedding vectors into a new coordinate system. Each principal component is a new axis that captures as much variation in the data as possible. The first components therefore contain most of the information. By visualizing only the first two components, you can often identify semantic patterns:

[source, python, indent=0]
----
# Perform PCA with 2 components
pca = PCA(n_components=2)
df_reduced = pca.fit_transform(embeddings_df)

# Create a new DataFrame with reduced dimensions
df_reduced = pd.DataFrame(df_reduced, columns=["PC1", "PC2"])
df_reduced["text"] = text_chunks  # Add original text chunks for labeling

# Create a scatter plot
plt.figure(figsize=(8, 6))
plt.scatter(df_reduced["PC1"], df_reduced["PC2"])

# Add labels to each point
for i, label in enumerate(df_reduced["text"]):
    plt.text(df_reduced["PC1"][i], df_reduced["PC2"][i], label, fontsize=9)

plt.xlabel("Principal Component 1")
plt.ylabel("Principal Component 2")
plt.title("PCA Scatter Plot")

# Save the plot
plt.savefig("../principal_component_plot.svg", format="svg")
----

The plot in <<image_reduce_dimensions>> shows the results. In this example, sentences about food and drinks appear grouped on the right, weather-related sentences in the lower left, and sentences about flowers in the upper left.

==== Discussion

Dimensionality reduction works by projecting high-dimensional vectors onto a lower-dimensional space (typically 2D or 3D) while preserving relative distances between points. PCA finds the directions of maximum variance in the data and uses them as the new axes. This means semantically similar text chunks that are close in 1,536-dimensional space often remain close in 2D.

Use visualization during development to verify that your embedding model clusters semantically similar content together. This validates that "legal documents" group separately from "marketing materials" before deploying the system. Visualization also builds stakeholder trust in regulated industries by making retrieval behavior tangible during demos.

Do not use 2D plots in production for diagnostics. They simplify 1,536 dimensions down to 2, which means they cannot show all relationships. Use them during development to verify clustering behavior, but in production track retrieval metrics like precision@k instead.

The main tradeoff is simplicity versus accuracy. t-SNE and UMAP preserve local structure better than PCA but take longer to compute and can produce misleading patterns if parameters are poorly tuned. PCA is faster and deterministic but may not capture non-linear relationships as well.

=== Calculating the Distance Between Embeddings

==== Problem

You want to measure how similar two pieces of text are by calculating the distance between their embedding vectors.

==== Solution

Calculate cosine similarity between embedding vectors using NumPy or the sentence-transformers library.

This recipe uses OpenAI text embedding models to generate embeddings and NumPy to calculate cosine similarity.

[source,bash]
----
pip install openai numpy sentence-transformers pandas
----

The following code snippet generates embeddings for three historical statements and one user question. The goal is to find the historical fact that best matches the user's question, which asks for information about diseases in history.

[source, python, indent=0]
----
import numpy as np
from numpy.linalg import norm
import pandas as pd
import os
from openai import OpenAI

text_chunks = [
    "The Great Fire of London in 1666 destroyed over 13,000 houses.",
    "Julius Caesar was assassinated on the Ides of March (March 15) in 44 BCE.",
    "The Black Death is estimated to have killed nearly one-third of the population.",
]

users_question = "Tell me something interesting about diseases in history"

embeddings_df = pd.DataFrame(text_chunks, columns=["text_chunk"])

client = OpenAI()
embeddings = []

def create_embeddings(text_chunk, client):
    embedding = (
        client.embeddings.create(input=[text_chunk], model="text-embedding-3-small")
        .data[0]
        .embedding
    )
    return embedding

# Apply function create_embeddings to the correct column
embeddings_df["embedding"] = embeddings_df["text_chunk"].apply(
    create_embeddings, client=client
)

users_question_embedding = create_embeddings(
    text_chunk=users_question, client=client
)
----

The next code snippet calculates cosine similarity using NumPy.

[source, python, indent=0]
----
# create a list to store the calculated cosine similarity
cos_sim = []

def calculate_cosine_similarity(text_chunk_embedding, users_question_embedding):
    A = text_chunk_embedding
    B = users_question_embedding

    # calculate the cosine similarity
    cosine = np.dot(A, B) / (norm(A) * norm(B))
    return cosine

# Apply function calculate_cosine_similarity to the correct column
embeddings_df["similarity"] = embeddings_df["embedding"].apply(
    calculate_cosine_similarity, users_question_embedding=users_question_embedding
)
----

==== Discussion

Cosine similarity measures the angle between two vectors rather than their absolute distance. For RAG systems, this is the preferred distance metric because it focuses on semantic direction rather than magnitude. A short query like "reset password" and a long paragraph explaining password reset procedures point in the same semantic direction and receive a high similarity score, even though their vector magnitudes differ significantly.

<<image_similarity_measures>> shows three common distance metrics used with embeddings: cosine similarity, Euclidean distance, and Manhattan distance.

[[image_similarity_measures]]
.Common Distance Metrics for Measuring Vector Similarity
image::img/ch05_images/similarity_measures.png[Comparison diagram of three vector distance metrics shown graphically. Cosine distance displays two vectors with angle marked between them. Euclidean distance shows direct line between two points. Manhattan distance shows path following grid-aligned blocks. Each metric illustrated with two points or vectors in 2D space]

This robustness to length differences matters because user queries are typically much shorter than retrieved documents. Without normalization, longer documents would dominate rankings simply due to magnitude, not relevance.

Use cosine similarity for standard RAG retrieval with modern transformer-based embeddings. It works well across different text lengths and captures semantic meaning effectively. Use Euclidean distance when vector magnitude carries semantic meaning, which is rare in modern embeddings but can occur in specialized domains where embedding norms encode additional information. Use dot product for speed in production systems where you can normalize vectors once during indexing and reuse them, avoiding repeated normalization overhead.

Avoid Manhattan distance unless working with high-dimensional sparse vectors where it offers computational advantages. In practice, cosine similarity remains the default for over 95% of RAG systems using transformer-based embeddings.

=== Choosing the Right Embedding Model

==== Problem

You need to pick the right embedding model for your project.

==== Solution

Follow these steps to select the right embedding model for your RAG system:

1. Check benchmarks: Review the Massive Text Embedding Benchmark (MTEB) leaderboard at https://huggingface.co/spaces/mteb/leaderboard[Hugging Face] to see model performance across tasks. For multilingual systems, check MIRACL benchmark scores.

2. Identify deployment constraints: Determine if you can use commercial cloud APIs (OpenAI, Google, Cohere) or need local deployment due to data sensitivity or offline requirements.

3. Establish baselines: Start with proven models like OpenAI's `text-embedding-3-small` when using commercial providers or `all-MiniLM-L6-v2` for local deployment.

4. Test with real data: Run end-to-end tests using 50-100 representative queries from your actual use case. Measure retrieval accuracy by checking if the correct documents appear in the top results.

5. Compare alternatives: If baseline accuracy is insufficient, test a larger model (e.g., `text-embedding-3-large`) with the same query set to quantify the improvement.

6. Measure performance: Use your vector database's query endpoint to measure average retrieval latency. Ensure it meets your application's requirements (<100ms for interactive apps).

7. Calculate costs: For cloud APIs, multiply expected monthly query volume by per-token pricing. Compare against baseline to validate budget fit.

The main decision is whether you can use commercial cloud models or need open-source models for local deployment. For RAG applications, commercial models like `text-embedding-3-small` or Google's `text-embedding-004` work well for most use cases.

==== Discussion

<<table_embedding_model_selection>> provides guidance on selecting models based on your use case.

[[table_embedding_model_selection]]
.Embedding Model Selection Criteria
[cols="2,3", options="header"]
|===
|Use Case |Recommended Approach

|Large datasets (>1M documents) or high query volume (>1000/day)
|Prioritize speed and cost with smaller models

|Critical accuracy needs (legal, medical, financial) with <100K documents
|Use larger models despite higher cost

|Real-time user-facing applications
|Favor models with <50ms latency

|Batch processing or offline indexing
|Accuracy can outweigh speed
|===

Use cloud-based models (OpenAI's text-embedding-3-small, Google's text-embedding-004) when you can tolerate API latency and costs in exchange for state-of-the-art accuracy. These models excel at understanding nuanced queries and work well across multiple languages without retraining.

Use open-source models (all-MiniLM-L6-v2, BGE-small-en-v1.5) when data cannot leave your infrastructure due to compliance requirements, when API costs exceed budget constraints at your query volume, or when you need offline operation. The accuracy gap has narrowed considerably—modern open-source models approach commercial performance for many retrieval tasks.

Avoid oversizing your embedding model. If your baseline tests with text-embedding-3-small show 85% retrieval accuracy and upgrading to text-embedding-3-large achieves 87%, the 2% improvement rarely justifies doubling costs and latency for most applications. Focus optimization efforts on chunking strategy and retrieval configuration instead.

The main risk is committing to a model without validating on your actual data. Benchmarks like MTEB measure general performance across diverse tasks, but your specific domain (legal contracts, medical records, code documentation) may behave differently. Always test with 50-100 real queries from your use case before production deployment.

[NOTE]
====
Embedding models have not advanced as rapidly as LLMs in recent years. Many RAG systems built years ago still use OpenAI's text-embedding-ada-002 because the accuracy remains sufficient for retrieval tasks. This stability means model selection is a one-time decision that rarely needs revisiting.

=== Generating Embeddings for Images and Text Using CLIP

==== Problem

You want to classify images or perform cross-modal matching between images and text using embeddings.

==== Solution

Use Contrastive Language-Image Pre-training (CLIP) to generate embeddings for both images and text, enabling cross-modal matching and classification.

<<image_clip_for_retrieval>> illustrates how you can use CLIP as part of your retrieval system:

. Generate embeddings for all images and text you want to add to the vector store.
. When a user asks a question, use CLIP to generate an embedding for the query and search the vector store.
. Compare the newly generated embedding vector to the embedding vectors stored in the vector store.
. Finally, send the retrieved images and text to a multimodal model that can interpret both at once and answer the user's question.

[[image_clip_for_retrieval]]
.CLIP-Based Multimodal Retrieval Architecture
image::img/ch05_images/clip_for_retrieval.png[Workflow diagram for CLIP-based multimodal retrieval system. Shows four sequential steps: image and text sources generate embeddings, vector database storage, user query generates query embedding, similarity comparison retrieves matching images and text for multimodal model. Illustrates bridging images and text in shared embedding space]

This approach allows you to build a large image database and query it by asking questions, because a CLIP-based retriever can connect text and images in both directions.

The practical example in this recipe demonstrates classification with CLIP. While the earlier diagrams showed how CLIP enables multimodal retrieval in RAG systems, this code example focuses on classification because it clearly demonstrates CLIP's core capability: mapping images and text into a shared embedding space. An image classifier works similarly to a RAG retriever—both compare embeddings to find the closest match. With a few lines of code, you can build a classifier for images of cats and dogs. <<image_clip_create_embeddings>> shows how this works with CLIP. You generate embeddings for images and embeddings for descriptive text like "a photo of a cat" and "a photo of a dog." When you classify a new image, you compare its embedding to the text embeddings. The closest match determines the predicted label.

CLIP is open source, which means you can load it and run it on your local machine using torch. To preprocess images, you can use the Pillow library.

----
pip install transformers torch pillow

The following code loads the CLIP model to create embeddings for images and text chunks. The CLIP processor tokenizes the text and preprocesses the images. Next, CLIP generates the embeddings, and you compute similarity scores for each image-text pair. The output contains similarity scores between each image embedding and each text embedding. The probabilities are derived from these similarity scores using the softmax function, ensuring they sum to 1.

[source, python, indent=0]
----
import torch
from PIL import Image
from transformers import CLIPProcessor, CLIPModel

# Load the model and processor
model = CLIPModel.from_pretrained("openai/clip-vit-base-patch32")
processor = CLIPProcessor.from_pretrained("openai/clip-vit-base-patch32")

# Text and image inputs
descriptions = ["A photo of a cat", "A photo of a dog"]
images = [
    Image.open("../datasets/images/cat.jpg"),
    Image.open("../datasets/images/dog.jpg"),
]

# Disable gradient tracking since this code only runs inference
with torch.no_grad():
    inputs = processor(
        text=descriptions,
        images=images,
        return_tensors="pt",
        padding=True,
        truncation=True,
    )
    outputs = model(**inputs)

dot_products_per_text = outputs.logits_per_text

# Calculate probabilities
probabilities = dot_products_per_text.softmax(dim=1)
----

The final output is a probability matrix. The first column shows how likely each image is to contain a cat, and the second column shows how likely it is to contain a dog. In other words, it measures how similar each image is to the text descriptions.

<<screenshot_clip_probability>> shows the results. In this example, the probability that the first image shows a cat is 0.9999, which means the probability that it shows a dog is extremely low. Remember that the probability always sums to 1 across all classes, so if it is an image of an elephant, but elephant is not one of the classes, it will still assign a high probability to either cat or dog.

Rows represent input images, columns show class probabilities for cat and dog. Example values demonstrate high-confidence classification with softmax-normalized probabilities summing to 1.0]

==== Discussion

CLIP works by training on millions of image-text pairs from the internet, learning to map both modalities into a shared vector space. The key insight is that semantically similar content ends up close together in this space regardless of modality. An image of a dog produces a vector near the text "a photo of a dog" because the model learned this association during training.

The model requires no task-specific training—you simply provide candidate text descriptions and CLIP ranks them by similarity to the image.

Use CLIP for image classification when you have many possible categories and want to avoid training a traditional classifier. Adding new categories requires only writing new text descriptions, not retraining the model. This makes CLIP powerful for rapidly evolving taxonomies or when labeled training data is scarce.

Use CLIP for cross-modal retrieval in domains where images and text are tightly coupled, such as product catalogs where users might search by description or image, or scientific papers where figures relate closely to textual explanations.

However, for most RAG applications, a simpler approach works better: use multimodal models (GPT-5.2, Claude Sonnet 4.5) to generate text descriptions of images, then embed those descriptions with standard text embedding models. Store the text descriptions in your vector database and only pass the original image to the LLM when that chunk is retrieved. This approach leverages text embedding models that are optimized for semantic text matching, while CLIP's direct image-text mapping adds complexity.

[WARNING]
====
CLIP's main limitation is that it cannot handle text within images reliably. A photo of a street sign saying "No Parking" may not embed near the text "no parking" if the model treats it as a generic sign image. Extracting and embedding the text separately avoids this problem.
====

==== Problem

You want to route user questions to specific data subsets (e.g., by topic, department, or document type) by training a classifier on text embeddings.

==== Solution

Train a classifier on text embeddings to route user questions to specific data subsets in your vector store. This pre-filtering step narrows the search space before semantic retrieval runs.

<<image_text_classifier_using_embeddings>> shows the two-step process: prepare your dataset by chunking documents and generating embeddings, then train a classifier using these embedding vectors as features to predict document categories.

====

====

The following code loads two example text files, one about the history of the Premier League and one about the history of deep learning, then applies recursive chunking to create text chunks.

[source, python, indent=0]
----
from langchain_text_splitters import RecursiveCharacterTextSplitter
import PyPDF2
import pandas as pd

pdf_files = [
    {
        "file_path": "../datasets/pdf_files/history_of_deep_learning.pdf",
        "label": "Deep_Learning",
    },
    {
        "file_path": "../datasets/pdf_files/premier_league_history.pdf",
        "label": "Premier_League",
    },
]

chunks_dict_list = []

# split both documents into chunks and append to the same list of dicts
for pdf_file in pdf_files:
    with open(pdf_file["file_path"], "rb") as file:
        reader = PyPDF2.PdfReader(file)

        text = ""
        for page in reader.pages:
            text += page.extract_text()

    text_splitter = RecursiveCharacterTextSplitter(
        chunk_size=200,
        chunk_overlap=0,
        length_function=len,
        is_separator_regex=False,
    )

    chunks = text_splitter.split_text(text)

    for chunk in chunks:
        chunks_dict_list.append({"text": chunk, "label": pdf_file["label"]})

chunks_df = pd.DataFrame(chunks_dict_list)
----

The next code snippet iterates over the just-created dataset and generates an embedding vector for each text chunk.

[source, python, indent=0]
----
client = OpenAI()

def create_embeddings(text_chunk, client):
    response = client.embeddings.create(
        input=[text_chunk], model="text-embedding-3-small"
    )
    embedding = response.data[0].embedding
    return embedding

chunks_df["embedding"] = chunks_df["text"].apply(create_embeddings, client=client)
----

The resulting DataFrame is the foundation for training the classifier.

The next code snippet sets the labels as the target vector `y`. The feature matrix `X` is defined by the embeddings. Using a lambda function, each dimension in the embedding vector is mapped to one column in the input matrix `X`. So the resulting input matrix has 1,536 columns, one for each dimension of the embedding vector.

Finally, the code snippet trains the Random Forest classifier using scikit-learn.

[source, python, indent=0]
----
from sklearn.ensemble import RandomForestClassifier
from sklearn.datasets import make_classification

y = chunks_df["label"]
X = chunks_df["embedding"].apply(
    lambda x: pd.Series(eval(x)) if isinstance(x, str) else pd.Series(x)
)

# Train a random forest classifier
clf = RandomForestClassifier()
clf.fit(X, y)
----

The next code snippet tests the model with a question that is clearly about football. The Random Forest predicts the probability for each class. In this example, the model is 94% confident that the question is related to the Premier League content.

[source, python, indent=0]
----

test_embedding = create_embeddings(
    text_chunk="What is the name of the top football league in England?",
    client=client,

X_test = [test_embedding]

# Predict the most likely class
predicted_classes = clf.predict(X_test)  # e.g. ['Premier_League']

==== Discussion

Classification routing works by training a model to map embedding vectors to predefined categories. The Random Forest classifier learns patterns in the 1,536-dimensional embedding space that distinguish topics. When a new query arrives, its embedding is fed to the classifier, which predicts the most likely category with a probability score.

This pre-filtering narrows the search space before semantic retrieval runs. Instead of searching all 100,000 documents in your vector store, the classifier routes sports queries to the 20,000 sports documents, reducing retrieval latency and improving precision.

Use classification routing when your vector store combines drastically different content types where semantic similarity can be misleading. A question about "market performance" might retrieve sports articles about team performance instead of financial data because embedding models see them as semantically similar. Classification prevents this by routing the query to the correct domain first.

Use it when you have clear, stable categories (sports, politics, finance) with sufficient training examples per category (at least 100-200 labeled chunks). The classifier needs enough examples to learn discriminative patterns in the embedding space.

Avoid classification routing when categories overlap significantly or when domain boundaries are fuzzy. Questions about "sports betting regulations" span both sports and legal domains—forcing a single category loses relevant information. For overlapping domains, metadata filtering works better: assign category metadata fields during ingestion, then filter by `category IN ['sports', 'legal']` before semantic search. This preserves documents from multiple relevant categories without requiring a classifier.

Avoid it when your document collection is small (<10,000 documents) or homogeneous. The overhead of training and maintaining a classifier outweighs benefits when semantic search alone performs well. Start with semantic search. Add classification only when you observe cross-domain confusion in retrieval logs.

The main tradeoff is precision versus maintenance burden. Classification improves routing precision for distinct domains but requires labeled training data, periodic retraining as content evolves, and additional inference latency (typically 10-20ms). The classifier can also make mistakes—misrouting queries loses relevant documents entirely, unlike semantic search which might return suboptimal but still-relevant results.

[[recipe_hybrid_search_python]]
=== Improving Search Results with a Hybrid Search Approach

==== Problem

You want to improve retrieval quality by combining multiple search techniques instead of relying on a single one.

==== Solution

Combine BM25-based keyword search with vector similarity search, then merge their rankings using Reciprocal Rank Fusion.

<<hybrid_search>> shows the process step by step:

. A keyword search ranks documents based on exact term matches using BM25.
. An embedding model generates an embedding for the user's query.
. A semantic search ranks documents based on vector similarity.
. The rankings from both searches are merged into a single ranking.

[[hybrid_search]]
.Combining Keyword and Semantic Search with Reciprocal Rank Fusion
image::img/ch05_images/hybrid_search.png[Workflow diagram showing hybrid search process in four sequential steps. Left shows keyword search with BM25 ranking. Center shows embedding generation and vector similarity search. Right shows rank fusion combining both results using Reciprocal Rank Fusion.]

To implement hybrid search, you need three components:

* BM25 for keyword-based ranking, which is especially useful for product names, IDs, codes, and domain-specific terms.
* A text embedding model for semantic similarity search.
* A rank fusion method to merge both rankings into a single result list.

[source,bash]
----
pip install openai rank-bm25 sentence-transformers pandas
----

The following example uses three short text chunks. First, the code runs a BM25 keyword search.

[source, python, indent=0]
----
from rank_bm25 import BM25Okapi
import pandas as pd

text_chunks = [
    "The Great Fire of London in 1666 destroyed over 13,000 houses.",
    "Julius Caesar was assassinated on the Ides of March (March 15) in 44 BCE.",
    "The Black Death is estimated to have killed nearly one-third of the European population.",
]

# Tokenize text into words
tokenized_chunks = [chunk.split(" ") for chunk in text_chunks]

bm25 = BM25Okapi(tokenized_chunks)

user_query = "Tell me something interesting about diseases in history"
tokenized_query = user_query.split(" ")

# BM25 scores for each document
bm25_scores = bm25.get_scores(tokenized_query)

# Document IDs ordered by keyword relevance (best first)
keyword_ranking_doc_ids = (
    pd.DataFrame(bm25_scores, columns=["score"])
    .sort_values(by="score", ascending=False)
    .index
    .to_list()
)
----

Next, the code runs a semantic search using vector embeddings. Semantic search is strong when the query expresses intent and context, but it may miss exact identifiers or rare keywords.

[source, python, indent=0]
----
from sentence_transformers.util import cos_sim
from openai import OpenAI

client = OpenAI()

def create_embedding(text):
    return (
        client.embeddings.create(
            input=[text], model="text-embedding-3-small"
        )
        .data[0]
        .embedding
    )

embeddings_df = pd.DataFrame(text_chunks, columns=["text_chunk"])
embeddings_df["embedding"] = embeddings_df["text_chunk"].apply(create_embedding)

query_embedding = create_embedding(user_query)

# Compute cosine similarity
embeddings_df["similarity"] = cos_sim(
    embeddings_df["embedding"], query_embedding
)

# Document IDs ordered by semantic similarity (best first)
semantic_ranking_doc_ids = (
    embeddings_df
    .sort_values(by="similarity", ascending=False)
    .index
    .to_list()
)
----

At this point, you have two ranked lists of document IDs. The final step is to merge these rankings using Reciprocal Rank Fusion (RRF). RRF assigns higher scores to documents that appear near the top of both rankings.

[source, python, indent=0]
----
# Reciprocal Rank Fusion parameter
# Higher k reduces the influence of very top ranks
k = 60

# Build a table with one row per document
rrf_df = pd.DataFrame({"doc_id": range(len(text_chunks))})

# Map document IDs to their rank positions
keyword_rank_map = {
    doc_id: rank for rank, doc_id in enumerate(keyword_ranking_doc_ids, start=1)
}
semantic_rank_map = {
    doc_id: rank for rank, doc_id in enumerate(semantic_ranking_doc_ids, start=1)
}

rrf_df["keyword_rank"] = rrf_df["doc_id"].map(keyword_rank_map)
rrf_df["semantic_rank"] = rrf_df["doc_id"].map(semantic_rank_map)

# Reciprocal Rank Fusion score
rrf_df["rrf_score"] = (
    1 / (k + rrf_df["keyword_rank"]) +
    1 / (k + rrf_df["semantic_rank"])
)

# Final hybrid ranking
rrf_df = rrf_df.sort_values("rrf_score", ascending=False)

final_ranking_doc_ids = rrf_df["doc_id"].to_list()
----

Each row in the table represents one document. Documents that rank highly in both keyword search and semantic search receive the highest combined scores.

==== Discussion

Hybrid search combines two independent ranking signals that capture different aspects of relevance. Vector similarity search measures semantic closeness in embedding space. Reciprocal Rank Fusion merges both rankings by giving higher scores to documents that appear near the top of multiple lists.

The mechanism works because keyword and semantic signals are complementary. Keyword matching excels at exact terms (product IDs, medical codes, legal citations) where character-level precision matters. Semantic matching captures intent and handles synonyms, paraphrasing, and conceptual similarity that keyword search misses.

Use hybrid search when your corpus contains identifiers or specialized terminology that embeddings cannot capture reliably. Examples include product SKUs ("SKU-4792" must match exactly), legal statute numbers where "article 230" differs from "section 230," medical diagnosis codes (ICD-10 codes), and technical identifiers (API endpoint names, database table names). Keyword matching provides a critical ranking signal for these cases.

Use it when users mix natural language with precise terms in queries. A question like "How do I configure SSL for endpoint /api/v2/users?" benefits from semantic understanding of "configure SSL" and exact matching of the endpoint path.

Avoid hybrid search for pure knowledge retrieval where users phrase questions naturally without technical identifiers. A question like "How do I reset my password?" does not need keyword matching—semantic search captures the intent perfectly. Adding BM25 introduces complexity without improving results.

Avoid it when semantic search alone meets your quality requirements. Hybrid search adds computational overhead (you run two retrievers plus rank fusion) and increases system complexity. Start with semantic search. Add hybrid search only when you observe exact-match failures in your retrieval logs or user feedback.

The main tradeoff is recall versus complexity. Hybrid search improves recall for identifier-heavy queries but requires maintaining two retrieval systems, tuning the rank fusion parameter k, and handling edge cases where the two rankers disagree. The parameter k controls how much to favor top-ranked results—higher k (60-100) gives more weight to lower ranks, while lower k (10-20) strongly favors items that rank highly in both retrievers.
