== Foundation Models

Foundation models—including large language models and multimodal models—form the backbone of modern RAG systems. They are used both to generate answers for users and to prepare content before it is stored and retrieved.

In the generation step, language models analyze retrieved context and user questions to produce grounded responses. In the preparation step, multimodal models extract text from images, transcribe audio, summarize long documents, and enrich content with metadata that improves retrieval quality.

This chapter focuses on the language models and multimodal models used in both the ingestion phase—where content is processed, transformed, and prepared for storage—and the generation phase—where models analyze retrieved information and generate answers for users.

<<multimodal_models_content>> shows a typical multimodal workflow for processing video content.

1. Use a vision model to analyze video frames
2. Use speech to text to transcribe audio
3. Embed the resulting text using an embedding model
4. Retrieve relevant context when users ask questions
5. Generate answers using a language model

Every RAG system needs a generation model that interprets the retrieved content and generates the required output—whether that's answering a user question, producing a report, or completing another specific task. The following recipes show how to design effective prompts, choose appropriate models, and generate structured outputs.

=== Defining a Suitable Prompt Template

==== Problem

You need to define an effective prompt template for the generation step of a RAG application.

==== Solution

For RAG applications, prompts follow a structured pattern. A suitable prompt template consists of four key components:

1. A role that defines how the assistant should behave
2. An instruction that describes the task
3. The retrieved context the model must rely on
4. Output requirements that define how the answer should look

This structure guides the model toward grounded responses. By explicitly instructing the model to use only the retrieved context, users can later review the sources and verify that the answer is based on real information rather than hallucinated facts.

<<prompt_structure_rag>> shows the high-level structure of such a prompt.

[[prompt_structure_rag]]
.Prompt Structure in RAG Applications
image::img/ch02_generation_images/prompt_structure_rag.png[Prompt Structure in RAG Applications, width=600]

To make this more tangible, consider an assistant that supports an internal purchasing team. The assistant has access to internal policy documents, contract clauses, and supplier notes. All this information is stored in a vector database and retrieved at query time to answer questions in a grounded way.

The following example shows a simple prompt template for this use case.

----
You are a procurement analyst who explains internal policies in a
simple and reliable way.

Read the retrieved context and answer the user's question using
only the information from the retrieved context.

If the answer is not covered in the context, say that the
information is not available in the provided context.

[Context]
{{context}}

[User Question]
"Do our standard supplier contracts include a minimum warranty period?"

[Output Requirements]
Short answer. Clear wording. Up to 120 words.
----

This prompt instructs the model to analyze the retrieved context and generate an appropriate answer based solely on that information. This is a classic chatbot setup, where the assistant is connected to a vector store containing domain-specific knowledge. Because the model is explicitly instructed to stick to the context, every answer remains traceable to real source material.

==== Discussion

Prompt templates work by creating consistent structure that constrains model behavior. The role field primes expectations about expertise level and communication style. Instructions define success criteria explicitly instead of relying on implicit model assumptions. Context provides grounding in retrieved facts. Output requirements prevent format errors that break downstream processing.

Balance flexibility and control. When templates are too loose, models inject training data and fabricate citations. When too strict, models refuse to answer edge cases that fall partly outside retrieved context. Test with real queries and adjust based on failure patterns.

Use structured templates when downstream systems parse model output or when consistency matters more than creativity. Don't use them for exploratory conversations where rigid structure limits useful responses. Templates add token overhead—every retrieval call pays this cost, so keep templates concise.

=== Selecting the Right Language Model for Your Task

==== Problem

You need to choose a suitable generation model for your RAG system. Picking a model that is too weak leads to unreliable answers. Picking a model that is too powerful can make your system slow and expensive.

==== Solution

All major providers offer model families in multiple sizes. The range goes from ultra-efficient models to reliable everyday models and up to powerful flagship and reasoning models for demanding tasks.

Cost is an important factor when using LLMs. Commercial LLMs charge separately for input and output tokens. Output tokens are often significantly more expensive because the model must generate each token one at a time while considering all previous tokens. Input tokens are processed in parallel during a single forward pass.

When choosing a provider, compare similar model tiers across vendors. For example, GPT-5 and Gemini 3 Pro both fall in the flagship tier, while GPT-5 Mini and Gemini 3 Flash compete in the efficient tier. Price differences within the same tier are typically marginal compared to the substantial cost variation between tiers.

* Ultra-efficient: ~€0.05–€0.30 per 1M input tokens
* Efficient: ~€0.30–€1.00 per 1M input tokens
* Flagship: ~€1.00–€5.00 per 1M input tokens
* Reasoning / Frontier: ~€2–€30 per 1M input tokens

==== Discussion

Model selection balances cost, latency, and accuracy. Your goal is to pick the smallest model that still meets requirements for each pipeline step.

Start with latency constraints. Real-time chatbots need responses within seconds. Users rarely wait more than 10 seconds unless answers provide exceptional value. For standard chatbot interactions with straightforward questions and manageable context—typically three to four retrieved chunks—ultra-efficient or efficient models often deliver adequate quality while responding faster than powerful models. In these scenarios, larger models do not provide enough additional value to justify the increased latency.

Batch jobs tolerate longer latency and can run for minutes or hours, so accuracy may justify using slower, more expensive models. A pipeline that reviews complex contracts can save significant money if slightly better extraction quality prevents costly errors, making reasoning models worth the extra cost. Simple tasks like extracting contract parties or expiry dates work well with cost-efficient models.

Don't use large reasoning models for simple classification or extraction tasks that efficient models handle reliably. Test at each tier—you may find ultra-efficient models work for 80% of queries, reserving expensive models for ambiguous cases only.

[TIP]
====
For complex workflows, break tasks into smaller steps and select the right model for each step. This lets you solve multi-step problems with efficient models because each call handles one clearly defined task instead of requiring reasoning across the entire workflow.
====

=== Generating Content Using the OpenAI API

==== Problem

You want to use remotely hosted LLMs from OpenAI to analyze and generate content, without deploying and operating models yourself.

==== Solution

OpenAI hosts its models on managed infrastructure and exposes them through API endpoints. This allows you to use powerful language models with minimal setup.

OpenAI offers different model families for different task profiles. Flagship models such as GPT-5 are suitable for complex reasoning tasks and are supported by smaller and faster variants like GPT-5-mini and GPT-5-nano. All of these models can process both text and images to generate responses.

<<openai_gpt_model_series>> shows the release of the main GPT model series.

[[openai_gpt_model_series]]
.OpenAI GPT Model Series
image::img/ch02_generation_images/gpt_model_series.png[OpenAI GPT Model Series, width=600]

You can find your API key in your OpenAI account settings. Search for "OpenAI API key" to create a new one.

Store the key in an environment variable named `OPENAI_API_KEY`. This is the default place for the OpenAI SDK to load the API key from.

[source,python]
----
pip install openai httpx
----

[NOTE]
====
If you work for a larger company with a strong Azure and Microsoft presence, you might not use OpenAI's public API directly. Instead, you can access the same OpenAI models through Microsoft's Azure OpenAI Service. Azure hosts models such as GPT-5, GPT-5-mini, GPT-5-nano, and text-embedding-3-small within the Azure ecosystem.
====

Communicating with OpenAI models follows a simple pattern. First, you create a client that connects to OpenAI's servers. Then you send messages with your prompt and receive a response with generated text.

Each message consists of two required fields. The `role` field indicates who is speaking, for example `system`, `user`, or `assistant`. The `content` field contains the actual message text.

The following code snippet shows how a message dictionary looks. You can add additional key-value pairs, but `role` and `content` are mandatory.

[source,json]
----
{
  "role": "user",
  "content": "What is RAG?"
}
----

The code snippet below shows a complete example. Messages are sent as a list of dictionaries. The first entry is usually a system message, followed by the first user message. After the prompt is sent, the model generates a response, which is appended to the message list.

[source,python]
----
from openai import OpenAI

def ask_with_context(context, question):
    client = OpenAI()

    messages = [
        {
            "role": "system",
            "content": "Answer based only on the provided context."
        },
        {
            "role": "user",
            "content": f"Context:\n{context}\n\nQuestion:\n{question}"
        },
    ]

    response = client.chat.completions.create(
        model="gpt-5.2",
        messages=messages
    )

    return response.choices[0].message.content


# Usage
context = "RAG stands for Retrieval-Augmented Generation."
question = "What does RAG stand for?"
answer = ask_with_context(context, question)
print(answer)
----

In addition to GPT models, OpenAI also provides speech-to-text and video generation models. Speech-to-text is relevant for RAG when you need to transcribe audio recordings, meeting notes, or customer calls before indexing them.

The following code snippet shows how to transcribe audio using the `gpt-4o-transcribe` endpoint. You upload an audio file and receive a transcript in return. You can use any file from the https://keithito.com/LJ-Speech-Dataset/[LJ Speech Dataset] as an example. LJ Speech is a collection of audio recordings from a single speaker reading various sentences.

[source,python]
----
import httpx
from openai import OpenAI

client = OpenAI(http_client=httpx.Client(verify=False))

with open(
    "..\\datasets\\audio_files\\LJ037-0171.wav",
    "rb",
) as audio_file:
    transcript = client.audio.transcriptions.create(
        model="gpt-4o-transcribe",
        file=audio_file,
    )

print(transcript.text)
----

==== Discussion

Using hosted foundation models requires minimal setup—API key, HTTP client, and you're generating text. Choosing between providers matters when you have specific constraints around cost, context windows, or regulatory requirements.

OpenAI's rate limits and throughput typically exceed competitors for high-volume production deployments. Switch to Google or Anthropic when you need longer context windows, cheaper high-volume inference, or specific multimodal capabilities.

GPT-5 handles complex reasoning, structured outputs, and tool use. For latency-sensitive workloads where speed matters more than maximum reasoning depth, consider GPT-4.1 or smaller variants like GPT-5-mini. GPT-4.1 optimizes for low latency and high throughput, making it better for real-time chat and customer support.

If you work in a company with strict cybersecurity requirements and already use Azure, you can use Azure OpenAI Services to process data within the Azure context without OpenAI capturing it for use on their own platforms.

[TIP]
====
When choosing between providers, focus on model capabilities and context window requirements rather than pricing. While cost differences between model tiers—from ultra-efficient to reasoning models—can be substantial (ranging from €0.05 to €30 per 1M input tokens), the price differences between providers within the same tier are marginal. The impact of selecting the right model tier for your use case matters far more than choosing between OpenAI, Google, or Anthropic based on small price variations.
====

==== See Also

* The https://platform.openai.com/docs/guides/embeddings[OpenAI Embeddings guide] explains how to use embedding models for similarity search and retrieval in RAG systems.

=== Generating Content Using Google's Gemini Models

==== Problem

You want to use Google's Gemini models to generate and analyze text and images.

==== Solution

Google aligned its API with OpenAI client library conventions, so you can reuse the same SDK. You only change the base URL so that the client sends requests to Google's generative language endpoint instead of OpenAI's.

<<google_gemini_model_timeline>> shows the main Gemini model releases so far.

image::img/ch02_generation_images/timeline_gemini_models.png[Google Gemini Model Timeline, width=600]

Install the OpenAI client library:

[source,python]
----
pip install openai
----

To use Gemini, you need an API key from Google AI Studio. Create a key with a few clicks and store it in an environment variable named `GOOGLE_API_KEY`. The example below reads the key from this variable.

The following code creates an OpenAI client that connects to Google instead of OpenAI. The structure is identical to using an OpenAI model. The only difference is the base URL defined when creating the client.

[[gemini_api_call]]
.Using the OpenAI SDK to call Google's Gemini API
[source,python]
----
import os
from openai import OpenAI

client = OpenAI(
    api_key=os.getenv("GOOGLE_API_KEY"),
    base_url="https://generativelanguage.googleapis.com/v1beta/openai/",
)

resp = client.chat.completions.create(
    model="gemini-3-flash",
    messages=[
        {"role": "user", "content": "What is the capital of France?"}
    ],
)

print(resp.choices[0].message.content)
----

Once this works, you can switch to other Gemini models by replacing the model name.

==== Discussion

As of early 2026, Gemini models are among the strongest options available, especially for multimodal tasks. They can interpret text, images, charts, and screenshots within a single reasoning chain and handle very large documents. Gemini 2.5 Pro supports context windows of around one million tokens and is designed for long-context reasoning across text, audio, images, video, and even source code repositories.

For everyday workloads, smaller models like Gemini 2.5 Flash and Gemini 2.5 Flash-Lite provide similar multimodal capabilities at much lower cost and higher speed, which makes them a strong choice for many RAG pipelines.

In practice, Gemini can act as a drop-in replacement for OpenAI models. The main reason to choose Gemini today, particularly Gemini 2.5 Pro, is its strong multimodal performance combined with robust long-context handling. Choose Gemini over OpenAI when processing documents larger than 100,000 tokens or when combining images, audio, and text in a single request.

For low-latency, short-context interactions such as chat, RAG retrieval steps, and agent loops, OpenAI models typically deliver faster time-to-first-token than Gemini. Gemini's architecture is optimized for long-context and multimodal workloads, which can introduce additional overhead for small requests.

[TIP]
====
Use Gemini 2.5 Pro for strong multimodal reasoning or very long context, and Gemini 2.5 Flash or Flash-Lite for cost-sensitive, high-throughput RAG pipelines.
====

=== Generating Content Using the Anthropic API

==== Problem

You want to use Anthropic's Claude models to analyze content and generate text.

==== Solution

Anthropic provides a strong alternative to OpenAI and Google, especially when you need precise reasoning, reliable coding support, or mathematically accurate outputs.

[[anthropic_claude_model_timeline]]

To use the Anthropic API, create an account on the Anthropic website and generate an API key. You can generate the key in the https://console.anthropic.com/[Anthropic Console] under the API section. Purchasing a small amount of credits is required. Five dollars is usually enough to run the examples in this book. Store the key as an environment variable named `ANTHROPIC_API_KEY` so the Anthropic SDK can locate it.

While Google provides an OpenAI compatible endpoint, Anthropic uses its own protocol, which does not match what the OpenAI SDK expects. Because of this, you need to use the Anthropic SDK.

[source,python]
----
pip install anthropic
----

Use the official Anthropic Python SDK to interact with Claude models. The following example shows a simple request-response flow for sending a prompt and retrieving generated text. In a RAG setup, this call typically sits after the retrieval step, where retrieved documents are injected into the user message.

The example uses the `messages.create` method, which is the standard interface for communicating with Claude models. The model returns its response in the `content` field.

[source,python]
----
from anthropic import Anthropic
import os

client = Anthropic(api_key=os.environ["ANTHROPIC_API_KEY"])

response = client.messages.create(
    model="claude-sonnet-4.5",
    max_tokens=200,
    messages=[
        {
            "role": "user",
            "content": "Explain how vector databases work in "
                       "simple terms.",
        }
    ],
)

print(response.content[0].text)
----

==== Discussion

Claude models emphasize explicit reasoning and edge case handling. In practice, Claude tends to produce longer explanations and explicitly flags ambiguities rather than picking a plausible answer. This behavior makes Claude suitable for tasks where conservative reasoning matters more than speed.

Choose Claude when explicit edge case handling matters—legal document review, compliance analysis, and code generation benefit from this approach. Claude's extended thinking capability also helps with complex mathematical reasoning and multi-step logical problems.

Don't use Claude for high-throughput chatbots where users expect instant replies to simple queries, or when you need the fastest possible inference for batch jobs. Claude's deliberate reasoning trades speed for thoroughness.

Anthropic offers models in different sizes. Claude Haiku handles high-volume workloads efficiently. Claude Sonnet provides strong all-around performance. Claude Opus delivers deep reasoning for complex tasks. This structure parallels OpenAI's and Google's model families.

=== Running Open Source Models Locally with Ollama

==== Problem

You need to run language models locally because your data is too sensitive to send to external providers, or because self-hosting is more cost-effective at your API call volume.

==== Solution

A simple way to run models privately is Ollama. It is a free open source tool that lets you run open source LLMs directly on your own machine. Once installed, it starts a local service that behaves like the remote API endpoints from OpenAI and Google.

Before you can call Ollama from your Python code, you need two things:

* The Ollama runtime installed on your machine
* At least one local model downloaded and ready to use

Ollama is not a Python package. It is a system tool that runs a small local server in the background. This server loads the model, performs inference, and exposes an API on `localhost:11434` that your Python code can call.

To install Ollama, follow the instructions at https://ollama.com/download/[Download Ollama]. Installers are available for macOS, Windows, and Linux.

Once Ollama is installed, you still need to download the models you want to run. You do this with simple `ollama pull` commands. These commands fetch the model weights and store them locally so the model is ready to run.

The following code snippet shows how to pull three popular models, Llama 2, Mistral, and CodeLlama. You can choose other models as well. A full list is available at https://ollama.com/models[Ollama Models].

[source,bash]
----
# Pull models (run in terminal)
ollama pull llama2
ollama pull mistral
ollama pull codellama
----

Once Ollama is running, you can call it like any other API. The simplest approach is to reuse the same OpenAI SDK used for the OpenAI and Gemini APIs. Ollama exposes an OpenAI compatible endpoint at `http://localhost:11434/v1`, so your existing code barely needs to change.

The code snippet below shows how to use the OpenAI client to call a local Ollama model. You create a client that points to the local endpoint instead of OpenAI's servers, then send your prompt exactly as before. The only differences are the `base_url` and the model name.

[source,python]
----
from openai import OpenAI

# Point the client to your local Ollama server
client = OpenAI(
    base_url="http://localhost:11434/v1",
    api_key="ollama",  # Ollama does not require a real key,
                       # but the SDK expects one
)

response = client.chat.completions.create(
    model="qwen3:4b",
    messages=[
        {"role": "system", "content": "You are a helpful assistant."},
        {
            "role": "user",
            "content": "What is retrieval augmented generation?"
        },
    ],
)

print(response.choices[0].message.content)
----

This keeps your code structure consistent across providers. If you later switch from Ollama to OpenAI or Gemini, you only need to change the `base_url` and `api_key`.

[TIP]
====
You can also call Ollama directly using `curl` or the `requests` library if you prefer not to use an SDK:

[source,bash]
----
curl http://localhost:11434/v1/chat/completions \
  -H "Content-Type: application/json" \
  -d '{
    "model": "llama2",
    "messages": [{"role": "user", "content": "What is RAG?"}]
  }'
----

====

Once you have the basic setup working, you can experiment with different models to compare their performance and behavior.

In the next example, we evaluate multiple local models at once. The code loops over a list of installed Ollama models, sends them the same prompt, and collects their answers. This allows you to compare quality, speed, and consistency across models.

[source,python]
----
from openai import OpenAI

models = ["llama2", "mistral", "codellama"]
client = OpenAI(
    base_url="http://localhost:11434/v1",
    api_key="ollama"
)

for model in models:
    print(f"\n--- Testing {model} ---")
    response = client.chat.completions.create(
        model=model,
        messages=[
            {"role": "user", "content": "Explain RAG in one sentence."}
        ]
    )
    print(response.choices[0].message.content)
----

==== Discussion

Ollama handles model downloads and runs them on your CPU or GPU. Running models locally has limits—without a strong GPU or dedicated inference hardware, your laptop can only handle smaller models, and even those respond noticeably slower than API calls. For privacy-sensitive workflows, this tradeoff is often acceptable.

Very large models in the 70B parameter range, such as Llama 3.1 70B, are usually too large for most laptops. More realistic choices are smaller variants like Llama 3.1 8B or similar mid-size models. They offer solid quality while keeping hardware requirements manageable. Expect 8B models to require at least 8GB of VRAM; 13B models need 16GB or more.

Run models on your own hardware when you process regulated health or financial data that cannot leave your network, or when you make millions of API calls per month where hosting costs drop below API fees.

Don't use local models when your use case requires the latest reasoning capabilities or when development speed matters more than cost. Local model setup, fine-tuning, and maintenance consume engineering time that could go toward application features.

[WARNING]
====
Treat public leaderboards as screening tools, not as a final decision criterion. Common limitations include:

* Benchmark leakage / data contamination: Some benchmark questions and answers are publicly available and may have been included (directly or indirectly) in training data, inflating scores.

* Goodhart's Law / over-optimization: Once a benchmark becomes a target, model developers may tune specifically for that benchmark, improving the score without improving general usefulness.

* Mismatch with real-world usage: Your production setup (prompt templates, retrieval quality, tool use, long context, multilingual content, quantization, and latency constraints) can change results materially. A model that "wins" on a leaderboard may still perform worse on your own RAG queries.
====

=== Creating Structured Outputs with the OpenAI SDK and Pydantic

==== Problem

You want to extract insights from text and images, while ensuring the output from LLM and multimodal models follows a predefined schema with the correct data types.

==== Solution

The OpenAI SDK lets you define a response schema using a Pydantic model. This schema describes the fields and their data types that the model should return. Instead of working with raw JSON, the SDK validates the model output and returns a typed Python object.

<<figure_2_12_structured_outputs_pydantic>> shows a simple multimodal invoice analysis flow. The model extracts the invoice date, supplier, receiver, line items, currency, and total value. A Pydantic model describes these fields and enforces the expected data types.

[[figure_2_12_structured_outputs_pydantic]]
.Structured Output with Pydantic Models
image::img/ch02_images/generate_structured_output_metadata.png[Diagram showing a multimodal flow where an invoice image and prompt are sent to a model, which returns a validated Pydantic object.]

To use structured outputs, install the OpenAI SDK and Pydantic:

[source,bash]
----
pip install openai pydantic
----

You start by defining the structure you want the model to fill. The code in the following example defines Python objects for invoice extraction with nested structures using Pydantic's `BaseModel` class. It creates a `LineItem` to represent individual items on an invoice, and `Invoice` to represent the complete invoice with multiple line items. Every Pydantic model must extend `BaseModel` because it provides automatic type validation and parsing methods that convert raw model output into clean Python objects.

[source,python]
----
# pip install openai pydantic

from openai import OpenAI
from pydantic import BaseModel
from datetime import date
from typing import List

class LineItem(BaseModel):
    description: str
    quantity: int
    total: float

class Invoice(BaseModel):
    invoice_number: str
    invoice_date: date
    supplier: str
    items: List[LineItem]
    total_due: float
----

Once the structure is defined, the next step is to ask the model to populate it. The next code snippet sends an invoice image along with instructions to the OpenAI endpoint, and the OpenAI SDK returns a parsed `Invoice` object that already passed type validation.

[source,python]
----
result = client.responses.parse(
    model="gpt-5-mini",
    input=[{
        "role": "user",
        "content": [
            {"type": "input_text", "text": "Extract the invoice data."},
            {"type": "input_image", "image_url": "invoice.png"},
        ],
    }],
    response_format=Invoice,
)

invoice: Invoice = result.output_parsed
print(invoice)
----

The result is a validated `Invoice` object. Because the data already has the correct types, you can store it directly in a database or pass it to downstream workflow steps without additional parsing or manual checks.

==== Discussion

Structured outputs enforce a schema at inference time, ensuring the model returns validated fields rather than unstructured text. This works because the API constrains model generation to produce only valid JSON matching your Pydantic schema. Typical use cases include:

* Extracting contract details from emails in a sales system
* Automatically parsing invoices or order confirmations
* Reading metadata from technical drawings to label them consistently
* Decision-making workflows where output must be constrained to specific value ranges

Pydantic validation catches type mismatches or missing fields before they propagate downstream, making failures visible immediately instead of letting incorrect values silently flow through the system.

Use structured outputs when downstream systems depend on the data—database inserts, API calls, decision logic, and multi-step agent workflows all benefit from guaranteed field types. Don't use them for exploratory chat, creative writing, or when you want the model to choose its own output format.

Structured outputs add latency because the model must generate valid JSON conforming to your schema. They can also constrain useful answers when the schema doesn't match what the model wants to explain. Forcing a binary answer when the correct response is "it depends" loses nuance. Test whether your use case benefits more from structure or flexibility.
