== RAG Web Apps

Most generative AI projects start as experiments, and most never reach production. Fast prototyping matters, especially when your team lacks full-stack engineering support. You need a setup that lets data scientists build RAG-powered apps real users can test before committing to production infrastructure.

Streamlit is a Python framework for rapid web app development. It lets you build functional interfaces with a single script that covers frontend and backend. The framework provides prebuilt components you can assemble without low-level web development, though you're limited to what Streamlit currently offers.

Streamlit reruns your entire script on every user interaction. This simplifies development but creates overhead that doesn't scale beyond a few dozen concurrent users. For validating whether a GenAI app provides value, this tradeoff works in your favor.

For production applications with thousands or millions of users, alternative frameworks provide better scalability and performance. Django offers full-featured capabilities with authentication and complex workflows. Flask provides a lightweight and flexible foundation. FastAPI is optimized for API endpoints.

The recipes in this chapter build progressively. You'll start by creating a basic Streamlit app to understand the framework's core mechanics, then build a working RAG chatbot, and finally extend it to handle document uploads and queries.

[TIP]
====
In the early days of RAG, many applications defaulted to chatbots even when simpler interfaces would have worked better. Dashboards and search interfaces are often faster and more intuitive. Before choosing a chat interface, consider whether your use case actually benefits from conversational interaction.
====

You can find all the code examples for this chapter in the https://github.com/polzerdo55862/RAG-with-Python-Cookbook[book's GitHub repository].

=== Building Your First Streamlit App

==== Problem

You are not a web developer, but you still want to quickly turn your idea into a web app and deploy it.

==== Solution

Streamlit is a Python web framework that lets you build a fully functioning web app with a single script and a few lines of code. Install Streamlit to follow this recipe:

[source,console]
----
pip install streamlit
----

The following code builds a basic Streamlit app that shows a title, a text input, and a section that prints the user's input to the screen.

[source,python]
----
import streamlit as st

st.title("Simple Chatbot")
user_input = st.text_input("You:")
if user_input:
    st.write(f"Bot: You said '{user_input}'!")
----

To run the app, execute the following command in the terminal:

[source,console]
----
streamlit run streamlit_app.py
----

This command starts a local web server that hosts the app. Unless you configure it differently, Streamlit uses port 8501 by default, so you can open the app at:

[source]
----
http://localhost:8501
----

==== Discussion

Streamlit's simplicity is its main advantage. The script rerun model eliminates session handling, routing, and frontend-backend coordination. You write Python code that looks like a regular script, and Streamlit handles the web interface automatically. This makes state management trivial for prototypes.

The tradeoff is scalability. Every user interaction reruns the entire script from top to bottom, creating CPU overhead for each user. Beyond 50 concurrent users, this model becomes a bottleneck.

Use Streamlit for internal tools, proof-of-concept demos, and rapid iteration during requirements gathering. Don't use it for external apps with thousands of users (FastAPI with React scales better), apps requiring custom branding (Django offers more UI control), or apps needing fine-grained authentication (FastAPI integrates auth middleware more naturally).

The critical tradeoff is development speed versus scalability. You can prototype a working RAG app in hours, but refactoring to production infrastructure later takes weeks. When most experiments won't reach production, this favors Streamlit.

You can extend Streamlit's reach by offloading compute-heavy tasks to microservices. Keep Streamlit as a lightweight frontend while delegating authentication, ML inference, or database operations to dedicated APIs. This hybrid approach works for 100-500 users before requiring a full rewrite.

=== Building a Chatbot App Using Streamlit

==== Problem

You have designed a RAG workflow and want to integrate it into a chatbot app.

==== Solution

Streamlit provides features for building conversational UIs. In this recipe, you build a chatbot that lets users ask questions about the weather. The chatbot uses an external API to retrieve weather information and an LLM to interpret that data and answer the user's question.

. An external weather API is called with the extracted location and returns today's weather information.
. The weather information is sent back to the LLM, which interprets the user's question together with the provided context and formulates a response.

with st.chat_message("assistant"):

The next step is to implement logic that accepts user input and maintains chat history using Streamlit session state. The code template for a basic chatbot interface stores the conversation in a `messages` list.

Each entry in `messages` is a dictionary with the keys `role` and `content`. The `role` is either `user` or `assistant`. The `content` is typically the user's question or the assistant's response. By continuously appending to `messages`, you build the session history of all user inputs and assistant replies.

The code also uses `st.chat_message()` to alternately render the user's prompt and the assistant's response.

[source, python, indent=0]
----
import streamlit as st

st.title("Simple RAG Chat App")

if "messages" not in st.session_state:
    st.session_state.messages = []


def simple_rag(query):
    if "hello" in query.lower():
        return "Hello! How can I help you?"
    elif "rag" in query.lower():
        return (
            "RAG combines retrieval and generation for better "
            "responses."
        )
    else:
        return (
            f"You asked: '{query}'. A real RAG system would "
            f"search documents and generate a response."
        )


for message in st.session_state.messages:
    with st.chat_message(message["role"]):
        st.markdown(message["content"])

if prompt := st.chat_input("Ask a question"):
    st.session_state.messages.append({"role": "user", "content": prompt})
    with st.chat_message("user"):
        st.markdown(prompt)

    response = simple_rag(prompt)
    st.session_state.messages.append(
        {"role": "assistant", "content": response}
    )

    with st.chat_message("assistant"):
        st.markdown(response)
----

At this stage, the app logic is still a dummy function that contains some `if`/`else` logic. Next, you replace that dummy with the logic of a real RAG system.

In the basic RAG system built in this recipe, the retriever is represented by two API calls:

. The first API call retrieves the latitude and longitude for a given location.
. The second API call uses those coordinates to retrieve the weather for that location.

Before calling these APIs, you use an LLM to examine the user's query and determine whether it contains a location. A location is required for the weather API; without it, the question cannot be answered.


[source, python, indent=0]
----
import openai
import json


def extract_the_city_and_country(user_query):
    client = openai.OpenAI()

    prompt = (
        f"Extract the city and country from: '{user_query}'. "
        "Return as JSON with 'city' and 'country' keys."
    )

    response = client.chat.completions.create(
        model="gpt-5.2",
        messages=[{"role": "user", "content": prompt}],
        response_format={"type": "json_object"},
    )

    try:
        return json.loads(response.choices[0].message.content)
    except:
        return None
----

Next, call the Open-Meteo API to fetch the current weather data for the given coordinates. The following function fetches the weather data and returns the full API response.

[source, python, indent=0]
----
import requests


def get_current_weather_open_meteo(latitude, longitude):
    """
    Fetches current weather data from Open-Meteo for a given location.
    """
    base_url = "https://api.open-meteo.com/v1/forecast"
    params = {
        "latitude": latitude,
        "longitude": longitude,
        "current": (
            "temperature_2m,relative_humidity_2m,precipitation,"
            "weather_code,wind_speed_10m"
        ),
        # Automatically determine timezone based on location
        "timezone": "auto",
    }

    try:
        response = requests.get(base_url, params=params)
        # Raise HTTPError for bad responses (4xx/5xx)
        response.raise_for_status()
        weather_data = response.json()
        return weather_data
    except requests.exceptions.RequestException as e:
        print(f"Error fetching weather data: {e}")
        return None
----

The next step feeds the weather information into a prompt sent to the LLM. The model interprets the API results together with the user's question and generates a helpful answer.

The code below provides a basic prompt template, that includes the user's question and the weather data and asks the model to summarize the weather for the user.

[source, python, indent=0]
----
import openai


def create_weather_prompt(user_query, weather_data):
    if not weather_data:
        return "No weather data available."

    prompt = (
        "You are a helpful assistant. Based on the weather "
        "data below, answer the user's question in a clear "
        "and simple way.\n\n"
        f"User question: {user_query}\n\n"
        f"Weather data (JSON):\n{weather_data}\n"
        "Summarize the weather information so that it is "
        "easy for anyone to understand."
    )
    return prompt


def send_prompt_to_llm(prompt):
    client = openai.OpenAI()

    response = client.chat.completions.create(
        model="gpt-5.2",
        messages=[
            {"role": "system", "content": "You are a helpful assistant."},
            {"role": "user", "content": prompt},
        ],
    )

    return response.choices[0].message.content.strip()
----

Finally, combine the previously defined functions into a single RAG workflow that the Streamlit app can call whenever needed. In this recipe, the helper functions are moved into a separate Python module `app_helper_functions` to keep the main app file clean and make the RAG flow easier to follow. The code below shows the `perform_rag()` function that should be added to the `app_helper_functions` module:

[source, python, indent=0]
----
# In app_helper_functions.py

def perform_rag(user_query):
    location_data = extract_the_city_and_country(user_query)
    latitude, longitude = get_coordinates_for_city(
        location_data["city"], location_data["country"]
    )
    weather_data = get_current_weather_open_meteo(latitude, longitude)
    prompt = create_weather_prompt(user_query, weather_data)
    response = send_prompt_to_llm(prompt)
    return response
----

==== Discussion

Session state bugs stem from Streamlit's rerun behavior. Every user interaction triggers a script rerun, which resets all variables to their initial values. Data persists only if explicitly stored in `st.session_state`. Always check `if "messages" not in st.session_state` before accessing it to avoid `KeyError` exceptions.

Use session state for chatbots where conversation history matters. Don't use it for stateless apps like search interfaces or dashboards where each query is independent—session state adds unnecessary complexity.

The main risk is state leaking between users. Streamlit creates one session per browser tab, but single-tab testing misses multi-user bugs. If user A uploads a document and user B refreshes, does user B see user A's document? Test with two browser windows to catch this early.

For complex workflows, separate RAG logic from UI code: keep the Streamlit script under 100 lines, move API calls and prompt assembly to separate modules, and deploy compute-heavy operations (embeddings, large model calls) as Lambda functions or microservices. Use single-script structure only for demos. Use module separation when multiple developers work on the codebase or when the RAG logic will be reused outside Streamlit.

Debugging Streamlit apps is challenging because print statements appear out of order during reruns. Use the VS Code debugger instead. <<screenshot_create_new_debugger_config>> shows the setup: create a configuration with `streamlit` as the module, `run` as the first argument, and your app filename as the second. Set breakpoints to inspect `st.session_state` at each rerun.

=== Adding PDF Analyzer Functionality to Your Chatbot

==== Problem

You want to enable your chatbot to accept PDF uploads and analyze them using LLMs and multimodal models.

==== Solution

This recipe shows how to add upload functionality to your chatbot and then use multimodal models to extract and analyze the document text.

<<image_entity_extraction_web_app>> shows the high-level process. Because multimodal models work with images, such as JPEGs or PNGs, the first step is to split the PDF into individual page images. Then you iterate over all pages and use a multimodal model to extract text from each page. Finally, you concatenate the extracted page text into a single document text and run an entity/value extraction step over the full text.

[[image_entity_extraction_web_app]]
.Process for entity extraction web app
image::img/ch11_images/image_entity_extraction_web_app.png[]

The app uses multimodal models from OpenAI, along with `pdf2image` and `Pillow`, to preprocess PDFs and convert each page into an image.

[source, bash, indent=0]
----
pip install streamlit openai pdf2image pillow pydantic
----

The recipe builds a chatbot with drag-and-drop PDF upload. The following code defines a function that converts a PDF into images using the `pdf2image` library. It saves each page as a PNG and stores the resulting image paths in a list.

[source, python, indent=0]
----
from pdf2image import convert_from_bytes


def convert_pdf_to_images(pdf_file):
    # Read the PDF file and convert each page to an image
    # (PIL Image objects)
    images = convert_from_bytes(pdf_file.read())

    # Save each image to a temporary PNG file and return the file paths
    image_paths = []
    for idx, image in enumerate(images):
        temp_path = f"images/temp_page_{idx}.png"
        image.save(temp_path, "PNG")
        image_paths.append(temp_path)
    return image_paths
----

In the second step, you send each image to a multimodal model, which extracts the text.

The following code performs the OCR/extraction step. It uses a simple prompt that turns a multimodal model into an OCR assistant focused on text.

[source, python, indent=0]
----
from openai import OpenAI
import base64
from io import BytesIO

client = OpenAI()


def perform_ocr_and_extract_entities(image_paths):
    extracted_text = []

    # Prepare the system message for GPT-5.2 vision
    system_message = {
        "role": "system",
        "content": (
            "You are an OCR assistant. Extract all text from the "
            "provided images. Do not summarize or skip any content."
        ),
    }

    for image_path in image_paths:
        with open(image_path, "rb") as image_file:
            # Read image data and base64 encode it
            base64_image = base64.b64encode(
                image_file.read()
            ).decode("utf-8")

        # Create the image_url dictionary directly from the base64 string
        image_content = {
            "type": "image_url",
            "image_url": {"url": f"data:image/png;base64,{base64_image}"},
        }

        messages = [
            system_message,
            {
                "role": "user",
                "content": [image_content],
            },
        ]

        response = client.chat.completions.create(
            model="gpt-5.2",
            messages=messages,
            max_tokens=4096,
        )

        full_text = response.choices[0].message.content
        extracted_text.append(full_text)

    return extracted_text
----

From the extracted text, you can now run an entity extraction step. The following code shows how to extract person entities with fields like name, age, and city from the full document text. You can adapt the prompt to extract any other type of entity or value as needed.

[source, python, indent=0]
----
from openai import OpenAI
import json

client = OpenAI()

def extract_entities_from_text(extracted_text):
    system_message = (
        "Extract all people entities from the text as a JSON array "
        "of objects with fields: ID (int), Name (str), Age (int), "
        "City (str)."
    )
    text = "\n".join(extracted_text)
    response = client.chat.completions.create(
        model="gpt-5.2",
        messages=[
            {"role": "system", "content": system_message},
            {"role": "user", "content": text},
        ],
        max_tokens=1024,
    )
    extracted_data = response.choices[0].message.content

    return extracted_data
----

The last step is to combine these functions into a single chatbot application.

[source, python, indent=0]
----
st.title("Chat with File Upload")

uploaded_pdf = st.file_uploader(
    "Upload a PDF (optional)",
    type=["pdf"],
)

prompt = st.chat_input("Ask a question about the uploaded PDF")

if prompt and prompt.files:
    with st.spinner("Processing PDF..."):
        for uploaded_file in prompt.files:
            if uploaded_file.type == "application/pdf":
                images = convert_pdf_to_images(uploaded_file)
                extracted_text = perform_ocr_and_extract_entities(images)

                st.write("Extracted Text from PDF Pages:")
                for idx, page_text in enumerate(extracted_text, 1):
                    st.markdown(f"**Page {idx}:**")
                    st.write(page_text)

                extracted_data = extract_entities_from_text(extracted_text)
                st.write("Extracted Entities:")
                st.write(extracted_data)
----

==== Discussion

Multimodal models process images through vision transformers that recognize text, tables, and layout simultaneously. They handle scanned documents and forms better than traditional OCR because they understand spatial relationships like "this number is in the 'Total' column" or "this signature appears below the approval line."

Converting PDFs to images creates a uniform processing pipeline. Both scanned and digital PDFs become images, so one code path handles everything. This simplifies development but increases cost because you process pixels instead of text layers.

Use this approach when documents mix text, tables, and images (invoices, forms, research papers), when scanned documents have no text layer, or when layout context affects meaning. Don't use it for plain text PDFs (10-100x more expensive than PyMuPDF extraction), for real-time workflows requiring sub-second latency, or when processing thousands of pages daily (costs scale linearly with page count).

The critical tradeoff is extraction quality versus cost. For a 100-page document, text-layer extraction costs $0.05 compared to $0.50-$2.00 for multimodal OCR. Digital-native documents (PDFs created from Word, LaTeX, or web browsers) containing only paragraphs and headings don't benefit from multimodal processing.

Multimodal models occasionally hallucinate field values or skip sections when pages are rotated or low-quality. Always validate extracted data against expected schemas using Pydantic before writing to downstream systems. Production systems need field presence validation, value range checks, and manual review queues for low-confidence extractions.

You can extend the prompt to extract richer structure: table data in JSON format, image descriptions for figures and diagrams, heading hierarchies for document navigation, or form field mappings for structured data entry.

=== Connect Your RAG App to a SQL Database

==== Problem

You want to connect your RAG chatbot to a SQL database so users can ask questions about the data.

==== Solution

To let users ask natural language questions about SQL data, the system must generate valid SQL queries. This capability is called text-to-SQL.

<<overview_how_vanna_ai_works>> shows the process when the RAG system receives a new user request. First, all available database documentation and data models are embedded into a vector store. When a user asks a question, the system performs a semantic similarity search to find relevant parts of the database documentation, and uses it to let an LLM generate a suitable SQL query. The SQL query is then executed against the database. Finally, the retrieved data is combined with a prompt and instructions for the generation model, which uses the data as the basis for answering the user's question.

[[overview_how_vanna_ai_works]]
.Overview of the steps VannaAI takes to answer a user question
image::img/ch11_images/overview_how_vanna_ai_works.png[]

This recipe uses OpenAI LLMs for SQL query generation and final answer generation, with the Vanna AI framework handling text-to-SQL functionality and ChromaDB as the vector store backend. For the sample SQL database, a new SQLite database is generated and filled with sample data.

[source, bash, indent=0]
----
pip install streamlit openai vanna chromadb sqlite3
----

The first step is to set up the SQL database and fill it with sample data. SQLite is a lightweight, in-file database well suited for small projects. Because it's just a file, it is cost-efficient and requires little maintenance. However, it does not cover more advanced database features such as session and user management.

In the https://github.com/polzerdo55862/RAG-with-Python-Cookbook[book repository], you'll find a Python script that includes SQL statements to create the SQLite database and populate it with sample data. The sample database represents an online bookstore and includes tables for genres, clients, staff, deliveries, authors, books, and sales items.

The next step is to initialize Vanna AI. The following code creates a new class that combines the required Vanna functionality. In this recipe, that includes the OpenAI chat model and the ChromaDB vector store.

[source, python, indent=0]
----
class MyVanna(ChromaDB_VectorStore, OpenAI_Chat):

The next step "trains" the Vanna engine. This does not train an ML model; it preprocesses documentation and stores it in the vector store.

| SQL statements
| Example SQL queries that reflect common access patterns and business logic.
| `vn.train(sql="SELECT id, name FROM employees WHERE department = 'Sales'")`

| Question-SQL pairs
| Example user questions paired with the correct SQL query. This is the most effective training method.
| `vn.train(question="Show me all active users", sql="SELECT * FROM users WHERE status = 'active'")`
|===

The following code snippet loads DDL statements from the database and uses them to train Vanna. The first part retrieves the DDL directly from the database. The second part iterates over those DDL statements and calls Vanna's training function for each one.

[source, python, indent=0]
----
# Initialize Vanna
if "vn" not in st.session_state:
    st.session_state.vn = MyVanna(
        {
            "api_key": os.environ.get("OPENAI_API_KEY"),
            "model": "gpt-5.2",
            "path": "./chroma_db",
        }
    )
    st.session_state.vn.connect_to_sqlite("bookstore.db")

    # Train on database schema
    ddl_df = st.session_state.vn.run_sql(
        "SELECT sql FROM sqlite_master WHERE sql IS NOT NULL"
    )
    for ddl in ddl_df["sql"]:
        st.session_state.vn.train(ddl=ddl)
----

For this straightforward example, the DDL statements alone are sufficient because the bookstore database is self-explanatory. For more complex data models, you need additional documentation such as table relationships, column meanings, and value formats.

At this point, you have a working retrieval step and data you can feed into the generation step. Next, embed the functions into a Streamlit chatbot. The following code shows the complete implementation of the chatbot app, including the call to Vanna.

[source, python, indent=0]
----
import streamlit as st
import os
from vanna.openai import OpenAI_Chat
from vanna.chromadb import ChromaDB_VectorStore
from openai import OpenAI

class MyVanna(ChromaDB_VectorStore, OpenAI_Chat):
    def __init__(self, config=None):
        ChromaDB_VectorStore.__init__(self, config=config)
        OpenAI_Chat.__init__(self, config=config)

# Initialize Vanna
if "vn" not in st.session_state:
    st.session_state.vn = MyVanna({
        "api_key": os.environ.get("OPENAI_API_KEY"),
        "model": "gpt-5.2",
        "path": "./chroma_db"
    })
    st.session_state.vn.connect_to_sqlite("bookstore.db")

    # Train on database schema
    ddl_df = st.session_state.vn.run_sql(
        "SELECT sql FROM sqlite_master WHERE sql IS NOT NULL"
    )
    for ddl in ddl_df["sql"]:
        st.session_state.vn.train(ddl=ddl)

st.title("SQL Chat App")

# Chat interface
if prompt := st.chat_input("Ask about the bookstore"):
    # Generate and run SQL
    sql = st.session_state.vn.generate_sql(prompt)
    result = st.session_state.vn.run_sql(sql)

    # Generate answer
    client = OpenAI()
    answer = client.chat.completions.create(
        model="gpt-5-mini",
        messages=[{
            "role": "user",
            "content": (
                f"Answer based on this data: {result}\n"
                f"Question: {prompt}"
            )
        }]
    ).choices[0].message.content

    # Display
    st.chat_message("user").write(prompt)
    st.chat_message("assistant").write(answer)
    with st.expander("SQL Result"):
        st.write(result)

==== Discussion

Text-to-SQL democratizes database access by letting non-technical users query data through natural language. When the database is well-documented with 5-20 tables and clear relationships, users can quickly get answers to common questions like top N queries, filters, and aggregations without writing SQL themselves.

The approach works best when users can review generated SQL before execution. Showing the query lets users catch errors and builds trust in the system. This transparency also helps users learn SQL patterns over time.

Text-to-SQL has predictable failure modes. Models guess wrong metrics for ambiguous questions like "show me trends" because they lack business context. Complex joins across 5+ tables often time out or return incorrect results. Poor documentation leads to hallucinated column names where the model invents plausible but nonexistent fields like `customer_lifetime_value` when the actual column is `clv`.

Don't use text-to-SQL when users aren't SQL-literate and ask vague questions (they can't validate generated queries), when queries need business logic not in the database, or when you need deterministic behavior for compliance or audit trails (LLM output varies).

The agentic approach (<<chapter_agentic_rag>>) handles these cases better. Define 10-20 SQL query templates as tools with parameters. The model chooses which template to use and fills in parameters. This gives you deterministic queries with clear audit trails while allowing natural language input.

For production systems, start with the agentic approach. Add free-form text-to-SQL only if users explicitly request it and your database documentation is solid. The hybrid model—agentic templates for common queries, text-to-SQL for ad-hoc exploration—works well for analytics teams.

=== Deploying Your Streamlit App Using Docker and AWS

==== Problem

You need to deploy your app in a robust, reproducible, and scalable way.

==== Solution

This recipe shows how to deploy your Streamlit app using Docker containers on AWS. Docker is a containerization platform that packages your application with all its dependencies into a portable container image. For more information about Docker, see https://www.docker.com[Docker's official website].

On AWS, you'll use Amazon ECR (Elastic Container Registry) to store your Docker images and Amazon ECS (Elastic Container Service) to run the containers. ECS manages the container lifecycle, including scaling and health monitoring.

To follow the practical part of this recipe, you need:

* Docker Desktop installed on your local machine to build and test images. Docker Desktop is free for personal use, but enterprise users may need a paid license.
* An account with a cloud provider to deploy the container

This recipe describes AWS briefly, but you can use other providers as well. Major cloud providers (AWS, GCP, and Azure) offer free tiers with limited allowances that are often sufficient for small side projects.

To reproduce the container build and deployment, use a folder structure that includes:

* `Dockerfile`
* `requirements.txt` (Python dependencies)
* The Streamlit app code
* `entrypoint.sh` (starts the app)

The first step is to create the `Dockerfile`, which specifies all dependencies. The following code shows the content of the dockerfile.

[source,dockerfile]
----
# Dockerfile (example)
FROM python:3.9-slim

WORKDIR /app

COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

COPY . .

EXPOSE 8501

ENTRYPOINT ["bash", "entrypoint.sh"]
----


The dockerfile defines the steps which are executed within the docker container. It sets the working directory to `./app`. When copying files into the image, ensure that you create this working directory (in this case, the `app` folder) and then copy your repository files into it. After the files are copied, the image installs the requirements via `pip` and exposes port `8501`.

The last command executes the `entrypoint.sh` script whenever the container starts. This script starts the Streamlit app and sets the server port so the app can be reached at a known address.

Now you can use the Dockerfile to create the actual Docker image. Open your terminal or command prompt, navigate to the directory where your Dockerfile is located, and execute the following command.

[source,console]
----
docker build -t rag-streamlit-app:latest .
----

This builds your image. Test it locally before deploying:

[source,console]
----
docker run -p 8501:8501 rag-streamlit-app:latest
----

Open `http://localhost:8501` to verify the app works. If you see the Streamlit interface, the container is ready for deployment.

*Deploy to AWS:*

1. Install AWS CLI
2. Create ECR repository: `aws ecr create-repository --repository-name rag-streamlit-app`
3. Push image (follow authentication commands from ECR console)
4. Create ECS task definition pointing to your ECR image
5. Deploy task on ECS Fargate (serverless container runtime)

*Deploy to GCP:* Use Cloud Run. Upload the image to Google Container Registry and deploy with one command.

*Deploy to Azure:* Use Container Apps. The workflow is similar to GCP Cloud Run.

[WARNING]
====
Fargate charges per vCPU-hour and memory. A single container running 24/7 with 1 vCPU and 2GB RAM costs approximately $30 to $40 per month. Enable auto-scaling carefully. Unrestricted scaling during a traffic spike can generate unexpected costs. Set maximum task count limits in your ECS service configuration.
====

==== Discussion

Docker packages the application with all its dependencies into a portable container. This makes deployment platform-independent and reproducible. Any developer can build the same image from the Dockerfile, ensuring consistency across development, testing, and production environments.

This recipe covers container creation and manual deployment. Production systems need three additional layers:

*Infrastructure as Code (IaC)*

IaC tools like Terraform or AWS CDK define your infrastructure in version-controlled files. Without IaC, debugging production issues means manually clicking through consoles to remember configurations. IaC prevents configuration drift. When you manually update production through the console, your dev environment slowly diverges. IaC enforces that both environments are built from the same source files.

*CI/CD pipeline:*

Use GitHub Actions or GitLab CI to rebuild and redeploy on every commit to `main`. The pipeline runs tests, builds the Docker image, pushes it to ECR, and updates the ECS task definition. If tests fail, the pipeline blocks deployment. Manual deployment introduces human error. You might forget to run tests, build from the wrong branch, or skip a migration script. CI/CD pipelines make these mistakes impossible.

*Secrets management:*

Don't hardcode API keys in the Docker image. Images are stored in registries where they're visible to anyone with access. Use AWS Secrets Manager or environment variables injected by ECS at runtime. This keeps credentials out of version control and container registries. If an image leaks (through misconfigured registry permissions or compromised CI/CD credentials), attackers gain your API keys. Rotating credentials means rebuilding and redeploying every image. With secrets management, you rotate in one place.

For prototypes, manual deployment is fine. Add these layers when you're confident the app will run long-term, when multiple developers need to deploy, or when compliance requires audit trails.
