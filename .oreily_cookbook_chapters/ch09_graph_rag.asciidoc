== Graph RAG

Graph RAG extends basic retrieval with graph traversal, which lets you move through networks of entities and relationships instead of relying only on semantic similarity of isolated text embeddings.

Basic RAG systems split documents into chunks, embed them, and rely on vector search to surface relevant content. Vector search treats each chunk as an isolated unit, with no awareness of how pieces connect across a broader narrative. When information is spread across multiple parts of long documents or requires data from multiple sources, this approach misses relevant context. Dependencies, references, and relationships across sections get lost.

Graph RAG closes this gap. Instead of storing text only as embeddings, it extracts entities, forms explicit relationships between them, and combines this graph structure with the vector index. This produces context that is richer, more precise, and preserves explicit connections between entities.

<<graph_rag_vs_classic_rag>> illustrates the difference using contract document data. In a basic RAG setup, the system maintains a pool of isolated embedding vectors. In Graph RAG, every text snippet is anchored to its surrounding structure. Each clause is linked to its clause type, its company, its address, and the SLA it originates from. This structural context helps the model not only find relevant text, but truly understand where it belongs.

[[graph_rag_vs_classic_rag]]
.Graph RAG vs. Classic Vector Search
image::img/ch09_images/graph_rag_vs_classic_rag.png[Graph RAG vs. Classic Vector Search,role="half-width"]

To build a Graph RAG system, you replace the traditional retriever with a graph database. In this chapter, Neo4j is used for all graph examples.

Once the graph is populated, the retrieval flow typically follows four steps.

. Initial search: You begin with either vector search or full-text search to identify relevant nodes. These act as your anchor points.

. Graph expansion: Starting from the anchor nodes, you traverse the graph, usually through one or two hops, to gather related nodes and edges.

. (Optional) Filtering and ranking: You refine the expanded result set and keep only the nodes that add meaningful context.

. Context assembly and generation: You feed both the original anchor text and its connected context into the LLM.

This process combines semantic matching with structural reasoning, producing context that reflects both meaning and connections. <<phases_of_graph_rag>> shows the main retrieval process.

[[phases_of_graph_rag]]
.Phases of Graph RAG Retrieval
image::img/ch09_images/phases_of_graph_rag.png[Phases of Graph RAG,role="half-width"]

In this chapter you will build your first knowledge graph, populate it with text from documents, and enrich it with structured data.

[NOTE]
====
Graph databases deliver richer context by following connections between nodes. Graphs introduce additional complexity and cost compared to basic RAG systems. They require careful data modeling, structured ingestion, and more upfront work. When relationships matter and the final answer depends on how entities connect to each other, graphs unlock retrieval behavior that classic RAG systems cannot achieve.
====

Before inserting data, the following code defines constraints to prevent duplicates. Without constraints, the MERGE command may create duplicate nodes if matching logic is ambiguous. The `id` property on `SLA` and `Clause` nodes, and the `name` property on `ClauseType` nodes need to be unique.

[source,python,indent=0]
----
def create_constraints(driver):
    """Create uniqueness constraints for graph nodes."""
    constraints = [
        "CREATE CONSTRAINT sla_id IF NOT EXISTS " "FOR (s:SLA) REQUIRE s.id IS UNIQUE",
        "CREATE CONSTRAINT clause_id IF NOT EXISTS "
        "FOR (c:Clause) REQUIRE c.id IS UNIQUE",
        "CREATE CONSTRAINT type_name IF NOT EXISTS "
        "FOR (t:ClauseType) REQUIRE t.name IS UNIQUE",
    ]
    with driver.session() as session:
        for constraint in constraints:
            session.run(constraint)


driver = get_driver()
create_constraints(driver)

Parse the SLA document by splitting on section headings. The following code uses a regular expression to separate the document at each second-level heading (lines starting with `##`) and creates a `Clause` object for each section:

[source,python,indent=0]
----
@dataclass
class Clause:
    id: str
    title: str
    text: str
    order: int
    clause_type: str = "Other"


def parse_sla_file(path, sla_id):
    with open(path, "r", encoding="utf-8") as f:
        content = f.read()

    sections = re.split(r"^##\s+", content, flags=re.MULTILINE)[1:]
    clauses = []

    for idx, section in enumerate(sections, start=1):
        lines = section.strip().splitlines()
        if not lines:
            continue
        title = lines[0].strip()
        text = "\n".join(lines[1:]).strip()

        clauses.append(Clause(id=f"{sla_id}_C{idx}", title=title, text=text, order=idx))

    return clauses
----

With the clauses extracted, transform the list into the graph structure. The following code creates the `SLA` node with its title, then creates the `Clause` nodes and links them back to the SLA. Finally, it connects adjacent clauses with `NEXT` relationships.

[source,python,indent=0]
----
def write_sla_and_clauses(driver, sla_id, sla_title, clauses):
    """Write SLA and Clause nodes to Neo4j with their relationships."""
    with driver.session() as session:
        # Create SLA node
        session.run(
            """
            MERGE (s:SLA {id: $id})
            SET s.title = $title
            """,
            id=sla_id,
            title=sla_title,
        )

        # Create Clause nodes and link to SLA
        for c in clauses:
            session.run(
                """
                MERGE (cl:Clause {id: $id})
                SET cl.title = $title,
                    cl.text = $text,
                    cl.order = $order
                """,
                id=c.id,
                title=c.title,
                text=c.text,
                order=c.order,
            )
            session.run(
                """
                MATCH (s:SLA {id: $sla_id})
                MATCH (cl:Clause {id: $cid})
                MERGE (s)-[:HAS_CLAUSE]->(cl)
                """,
                sla_id=sla_id,
                cid=c.id,
            )

        # Connect adjacent clauses to preserve document order
        for prev, nxt in zip(clauses, clauses[1:]):
            session.run(
                """
                MATCH (a:Clause {id: $p})
                MATCH (b:Clause {id: $n})
                MERGE (a)-[:NEXT]->(b)
                """,
                p=prev.id,
                n=nxt.id,
            )


write_sla_and_clauses(driver, sla_id, sla_title, clauses)
----

Each clause needs a type based on keyword matching. The following code maps keywords like "availability" or "uptime" to clause types. Clauses that do not match any keyword pattern are labeled "Other".

[source,python,indent=0]
----
def infer_clause_type(title):
    """Infer ClauseType based on keywords in the title."""
    title_lower = title.lower()
    keywords = {
        "Availability": ["availability", "uptime"],
        "Support": ["support", "response time", "incident"],
        "Maintenance": ["maintenance"],
        "DataProtection": ["data protection", "gdpr", "privacy"],
        "Liability": ["liability"],
        "Termination": ["termination"],
    }

    for clause_type, words in keywords.items():
        if any(word in title_lower for word in words):
            return clause_type
    return "Other"


for c in clauses:
    c.clause_type = infer_clause_type(c.title)
----

Once each clause has a type assigned, create the `ClauseType` nodes and connect each clause to its type with an `OF_TYPE` relationship.

[source,python,indent=0]
----
def add_clause_types(session, clauses):
    # Create ClauseType nodes
    types = [{"clause_type": c.clause_type} for c in clauses]
    session.run(
        """
        UNWIND $rows AS row
        MERGE (t:ClauseType {name: row.clause_type})
    """,
        rows=types,
    )

    # Link clauses to their types
    links = [{"id": c.id, "type": c.clause_type} for c in clauses]
    session.run(
        """
        UNWIND $rows AS row
        MATCH (cl:Clause {id: row.id})
        MATCH (t:ClauseType {name: row.type})
        MERGE (cl)-[:OF_TYPE]->(t)
    """,
        rows=links,
    )


add_clause_types(driver.session(), clauses)
----

==== Discussion

This recipe models SLAs as a graph of contracts, clauses, and clause types, preserving both document structure and relationships. Constraints and indexes prevent duplicates and keep queries fast, while the clause order keeps the original document sequence intact.

Graph modeling works because it captures relationships that embeddings cannot, such as which clause belongs to which contract or which clause comes next. This makes it possible to compare clauses across documents, follow reading order, or verify whether a contract is missing a required clause.

Use a graph when questions require traversing relationships, for example comparing termination clauses across suppliers or checking which contracts lack a specific clause type. For simple semantic lookup inside a single document, vector search alone is usually enough.

The tradeoff is schema and maintenance overhead. You must design node and relationship types up front and keep them in sync as data changes, but this structure enables powerful queries that pure vector RAG cannot support.

def load_slas(driver, sla_csv_path):
    """Load SLA metadata and link to Company nodes."""
    df = pd.read_csv(sla_csv_path)
    df["effective_date"] = df["effective_date"].replace({"N/A": None})
    df["effective_date"] = df["effective_date"].where(
        df["effective_date"].notna(), None
    )
    print(f"Loading {len(df)} SLA records...")

    with driver.session() as session:
        session.run(
            """
            UNWIND $rows AS row
            MATCH (c:Company {supplier_id: row.supplier_id})
            MERGE (s:SLA {id: row.sla_id})
            ON CREATE SET s.title = row.title,
                          s.service_name = row.service_name,
                          s.governing_law = row.governing_law,
                          s.effective_date = CASE
                            WHEN row.effective_date IS NOT NULL
                            THEN date(row.effective_date)
                            ELSE NULL END
            MERGE (c)-[:HAS_SLA]->(s)
            """,
            {"rows": df.to_dict(orient="records")},
        )

This import performs two key actions. First, it ensures that each SLA node exists and sets its metadata fields such as title, service name, governing law, and effective date. Second, it creates the `HAS_SLA` relationship that links each supplier to the contracts they hold.

This connection is crucial for queries that combine business context with contract content, such as "Which high-spend suppliers lack a termination clause?".

==== Discussion


*When to enrich graphs with structured data*

Use structured enrichment when retrieval depends on business context. Questions like "Which high-spend suppliers lack termination clauses?" or "Show me data protection clauses for German healthcare companies" require both contract text and entity attributes in the same query. This pattern is central to procurement, compliance, vendor management, and any domain where documents only make sense in relation to the entities they describe.

*When not to enrich graphs with structured data*

Skip enrichment if your questions are purely document-centric. If you only need "What does the Acme Corp contract say about support?" a simple clause lookup is enough. Importing and maintaining business data only pays off when it actually changes what gets retrieved. If metadata rarely influences selection, keep it outside the graph.

*Key tradeoffs*

Adding structured data increases operational complexity. Attributes like spend, addresses, or organizational structure change over time and must stay in sync with source systems. Stale data leads to wrong filters, for example marking a supplier as low-spend when it is not. When those filters significantly narrow the search space before semantic ranking, the accuracy gains usually justify the effort.

*How it differs from pure document graphs*

The earlier recipe modeled only document structure, such as SLAs, clauses, and clause types. This recipe adds business entities and their attributes as a second dimension. The result is a hybrid knowledge graph that combines content structure with business context, which is what distinguishes enterprise-grade Graph RAG from document-only graphs.

def clauses_of_type(clause_type):
    """List all clauses of a specific ClauseType across suppliers."""
    cypher = """
    MATCH (c:Company)-[:HAS_SLA]->(s:SLA)-[:HAS_CLAUSE]->(cl:Clause)
    MATCH (cl)-[:OF_TYPE]->(t:ClauseType {name: $clause_type})
    RETURN c.name AS company,

           cl.title AS clause_title,

    ORDER BY company, sla_id, clause_order

        return [r.data() for r in session.run(cypher, clause_type=clause_type)]

def high_spend_missing_termination(min_spend):
    """Return companies above min_spend whose SLAs lack a termination clause."""
    cypher = """
    MATCH (c:Company)-[:HAS_SLA]->(s:SLA)
    WHERE c.spend_2024 > $min_spend
    OPTIONAL MATCH (s)-[:HAS_CLAUSE]->(cl:Clause)-[:OF_TYPE]->(t:ClauseType {name: "Termination"})
    WITH c, s, count(cl) AS num_termination
    WHERE num_termination = 0
    RETURN c.name AS company,
           c.spend_2024 AS spend_2024,
           s.id AS sla_id
    ORDER BY spend_2024 DESC
    """
    driver = get_driver()
    with driver.session() as session:
        return [r.data() for r in session.run(cypher, min_spend=min_spend)]

def eu_data_protection_clauses(countries: list[str]):
    """Retrieve data protection clauses for suppliers in given EU countries."""

    WHERE a.country IN $countries

==== Discussion

Structural retrieval works by navigating the graph instead of searching text. You start from a known node and follow relationships to reach the information you need. If you know a specific SLA or company, you can go directly from that node to its clauses. If you want to compare the same kind of content across many contracts, you start from a `ClauseType` and collect all clauses of that type. If business rules matter first, you filter companies or contracts before looking at any text.

Use direct lookups when you know the exact document or entity you are interested in. Use type-based queries when you want to compare similar clauses across many documents. Use filtered searches when attributes like spend, region, or industry determine which data should be included.

Structural queries are fast and precise because they return only the nodes that match your labels and filters. Their limitation is that they depend on the quality of the graph structure. If your taxonomy is incomplete or inconsistent, relevant content can be missed. The next recipe adds semantic search to compensate for this by finding similar meaning even when labels do not line up exactly.

Compared to vector-only RAG, graph-based retrieval combines structure and semantics. Business rules and relationships can narrow the search space before semantic matching, or they can be used to validate and aggregate results after a semantic search.

Search the entire corpus using natural language queries. Return the top `k` most similar clauses based on their embeddings:

def semantic_search(query, top_k=5):
    """Find clauses semantically similar to the query."""
    driver = get_driver()
    emb = create_embedding(query)
    cypher = """
    CALL db.index.vector.queryNodes(
        "clause_embeddings", $top_k, $embedding
    )
    YIELD node, score
    RETURN node.title AS title,
           node.text AS text,
           score
    ORDER BY score DESC
    """
    with driver.session() as session:
        rows = [r.data() for r in session.run(cypher, top_k=top_k, embedding=emb)]
    driver.close()
    return rows
----

Combine semantic search with graph filters to narrow down results. This example uses an industry filter:

def hybrid_search_by_industry(query, industry, top_k=5):
    """Combine semantic search with industry filtering."""
    driver = get_driver()
    emb = create_embedding(query)
    cypher = """
    CALL db.index.vector.queryNodes(
        "clause_embeddings", $top_k, $embedding
    )
    YIELD node, score
    MATCH (node)<-[:HAS_CLAUSE]-(s:SLA)<-[:HAS_SLA]-(c:Company)
    WHERE c.industry = $industry
    RETURN c.name AS company,
           s.id AS sla_id,
           node.title AS clause_title,
           node.text AS clause_text,
           score
    ORDER BY score DESC
    """
    with driver.session() as session:
        rows = [
            r.data()
            for r in session.run(cypher, top_k=top_k, embedding=emb, industry=industry)
        ]
    driver.close()
    return rows
----

This function returns semantically similar clauses filtered by industry. The results include company name, SLA ID, clause title and text, along with similarity scores.

==== Discussion

This recipe combines vector search with graph filtering. Business rules such as industry or spend narrow the candidates first, then semantic similarity ranks the remaining clauses so the model sees only relevant text with company and SLA context.

Use hybrid search when queries mix meaning and business constraints. When labels like ClauseType are reliable, a pure Cypher query is simpler and faster.

The tradeoff is overhead. You must maintain both embeddings and graph structure, and vector search adds cost and latency. In return, you get queries that neither graphs nor vectors can handle alone.

Compared to basic RAG, Graph RAG does not return isolated chunks. It returns clauses together with their connected business context, which makes answers more precise and explainable.

=== Optimize the Knowledge Graph for RAG Systems

==== Problem

You want to optimize your graph when you measure performance or cost bottlenecks—such as slow queries, high token costs, or low retrieval precision.

==== Solution

Enhance the graph with optional components such as summaries, embeddings for entire SLAs, risk scores, domain ontologies or retrieval shortcuts.

Use an efficient LLM like `gpt-4o-mini` to summarize each clause and attach it as a new attribute `summary`:

[source,python,indent=0]
----
def summarize_clause(text):
    """Generate a summary for a clause using GPT-4o-mini."""
    prompt = f"Summarize this SLA clause:\n\n{text}"
    return (
        client.chat.completions.create(
            model="gpt-4o-mini",
            messages=[{"role": "user", "content": prompt}],
            max_tokens=120,
        )
        .choices[0]
        .message.content
    )

def add_clause_summaries():
    """Add summaries to all Clause nodes that don't have one."""
    driver = get_driver()
    with driver.session() as session:
        result = session.run(
            "MATCH (cl:Clause) WHERE cl.summary IS NULL RETURN cl.id AS id, cl.text AS text"
        )
        clauses = list(result)
        print(f"Generating summaries for {len(clauses)} clauses...")

        for i, row in enumerate(clauses, 1):
            s = summarize_clause(row["text"])
            session.run(
                "MATCH (cl:Clause {id:$id}) SET cl.summary=$s", id=row["id"], s=s
            )
            if i % 5 == 0:
                print(f"  Processed {i}/{len(clauses)} clauses")
    driver.close()
----

You can register a vector index for SLAs, just as you did for clauses. Summaries can be indexed and searched separately.

To speed up queries, you can store useful aggregates directly in the graph, such as:

* Count of availability clauses per supplier
* Combined lists of support obligations
* Flags for whether a clause type exists

This Cypher query shows a basic example that counts how many clauses of each type exist per company and stores the result as a new property on the `Company` node.

[source,cypher,indent=0]
----
MATCH (c:Company)-[:HAS_SLA]->(:SLA)-[:HAS_CLAUSE]->(cl:Clause)
      -[:OF_TYPE]->(t:ClauseType)
WITH c, t, count(cl) AS num_clauses
SET c[t.name + '_count'] = num_clauses
----

==== Discussion

These optimizations reduce cost and latency by moving work to ingestion time instead of query time. Clause summaries let the model scan many clauses cheaply before reading full text. SLA level embeddings make it possible to retrieve entire contracts without searching every clause. Aggregates avoid recomputing the same values on every query.

Each technique solves a different kind of bottleneck. Use summaries when you retrieve many clauses but only a few are relevant. Use aggregates when you keep calculating the same counts or flags. Use SLA embeddings when users ask about whole contracts rather than individual clauses.

Do not add these optimizations up front. Start with the baseline graph and measure how it performs. If queries are fast, token usage is acceptable, and answers are accurate, the simpler model is often enough.

The main tradeoff is maintenance. Summaries, aggregates, and embeddings must stay in sync as data changes, and they increase storage and ingestion time. They are most valuable when they remove a proven cost or performance problem.

Always retrieve the full clause text for the final answer. Summaries and cached values are meant for filtering and ranking, not for replacing the original data.
