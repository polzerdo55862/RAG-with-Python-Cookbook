== Getting Started with RAG

Large Language Models (LLMs) have transformed how we approach complex cognitive tasks—from writing production code to analyzing financial reports and translating between dozens of languages. Complementary foundation models now handle vision, speech synthesis and recognition, audio processing, image generation, and multimodal reasoning, all built on similar transformer architectures that can process and generate human-like content across multiple domains.

Despite these capabilities, these models have fundamental structural limitations. They do not have access to your private or confidential data unless you provide it. Their context windows limit how much information they can consider at once, which makes long documents expensive or impossible to analyse at once. And when they lack the right information, they tend to hallucinate rather than admit uncertainty.

Retrieval Augmented Generation (RAG) addresses all three problems at once. It gives the model controlled access to external knowledge, lets it work with far more information than fits into a single prompt, and grounds its answers in retrieved evidence instead of guesswork. When a user asks a question, the system first retrieves relevant information from a knowledge source and then passes that context to the model to generate a response.

<<basic_rag_chatbot>> shows the simplest form of a RAG system. A retriever searches a knowledge source such as a vector store or database and returns relevant passages. Think of the vector store as a specialized search engine that indexes your specific documents and knowledge base, rather than the entire web like Google. A generator, typically a LLM, uses that retrieved material to produce a grounded answer.

[[basic_rag_chatbot]]
.A RAG chatbot retrieves relevant information and generates contextual responses
image::img/ch01_images/harry_potter_basic_rag_chatbot.png[Basic RAG Chatbot Architecture]

RAG is most useful when knowledge is spread across many documents, when answers require synthesis rather than simple lookup, or when the data is too large or too diverse for a human to review. Modern systems often use multiple retrievers. One may search documents, another may query structured databases, and others may call external APIs. The model coordinates these tools to decide what information to use for each question.

<<harry_potter_multi_retrieval>> shows exactly this approach—a RAG system with multiple API endpoints that can search a Notion database, search the web, perform calculations, and access both SQL and vector databases to search the knowledge base. The model decides which retriever to call based on the question and combines the retrieved information to generate an answer. This architecture allows the system to handle a wide variety of questions.

[[harry_potter_multi_retrieval]]
.Example of a RAG system with multiple retrievers answering questions about Harry Potter books
image::img/ch01_images/harry_potter_multi_retrieval.png[Example of a RAG system with multiple retrievers answering questions about Harry Potter books]

While many people associate RAG primarily with chatbots, chat interfaces aren't always the optimal solution. Chat works well for exploratory questioning and initial user interactions, but often the best approach combines multiple interfaces. A typical workflow might start with a conversational interface to understand user intent, then transition to a dashboard, form-based application, or automated report once the system understands what the user actually needs. Many RAG systems also run entirely in the background, delivering results through APIs, scheduled reports, or integration with existing business applications.

This chapter walks you through setting up your environment and building your first basic RAG application.

All code examples are available in the https://github.com/polzerdo55862/RAG-with-Python-Cookbook[book's GitHub repository].

=== Identify High-Value RAG Use Cases for Your Organization

==== Problem

Your organization is exploring RAG and needs to identify use cases that deliver the most value.

==== Solution

Start by identifying use cases that solve concrete problems. Many RAG pilot projects fail because they're too complex, too expensive, or don't address real user pain.

Focus on two high-value areas where RAG delivers measurable impact:

1. Data extraction: Converting unstructured data (contracts, invoices, technical drawings, meeting notes) into structured, searchable information
2. Process automation: Handling repetitive tasks that require decision-making and adaptation

<<table_evaluating_rag_use_cases>> provides some guidance on how to evaluate different scenarios in terms of RAG fit and potential value.

|===
|RAG fit (1–5) |Use Case |Reasoning

|1
|"I want to chat with my quarterly report"
|Single document, low volume. Reading it directly or analysing with general apps (e.g., ChatGPT, Claude App) can do this well.

|2
|"Summarize this one document for me"
|General models (Claude, ChatGPT) already do this well. Custom RAG adds little value.

If information is missing or contains non-compliant parameters like welding thickness in this example, the system can automatically retrieve the supplier's contact information and generate a draft follow-up email.

This saves hours of manual review and speeds up issue resolution, an example for a high value RAG use case.

==== Discussion

RAG works for automation because LLMs can interpret intent and context, not just match patterns. Traditional automation requires explicit rules for every scenario. When a supplier email says "delayed due to weather" versus "shipment rescheduled," rule-based systems need separate handlers for each phrase. RAG-based systems understand both express the same operational impact.

This capability matters most when data is unstructured and variable. Use RAG when each input differs slightly but requires similar handling—customer emails, contract clauses, or incident reports. Don't use RAG for simple lookups, fixed-format data extraction, or tasks where rules never change. If you can write a regex or SQL query that handles 95% of cases, RAG adds unnecessary complexity and cost.

RAG trades simplicity for flexibility. Rule-based automation runs faster, costs less per operation, and fails predictably. RAG handles edge cases better but requires model hosting, prompt engineering, and evaluation frameworks. Factor in both token costs and engineering effort when comparing approaches.

Start with high-volume tasks where manual review creates bottlenecks. A system that processes 10 documents daily may not justify RAG development costs, but 1,000 documents daily does. Each implementation teaches you about prompt patterns, evaluation metrics, and failure modes that apply to subsequent projects.

Avoid complex multi-system integrations as first projects. Success requires both RAG expertise and organizational buy-in. After demonstrating value on focused use cases, expand to scenarios requiring cross-functional coordination or multiple data sources.

Notebooks keep data and models in memory. Load data once and run experiments repeatedly without restarting.

[source,python,indent=0]

----

Don't use notebooks when collaborating with teams unfamiliar with Jupyter. The execution order dependencies confuse developers accustomed to linear Python scripts. Similarly, avoid notebooks for code that must meet compliance requirements or pass through formal review processes—the JSON format makes auditing difficult.

=== Storing Secrets and API Keys with .env

==== Problem

You want to keep secrets like API keys out of your source code, while still reusing them across multiple projects.

==== Solution

Use a `.env` file to store secrets. This keeps API keys out of your codebase and prevents accidental commits to version control.

Store all secrets in a `.env` file and add it to your `.gitignore`. The `.gitignore` file lists files Git should not track, ensuring secrets stay local and never reach remote repositories.

This recipe demonstrates loading secrets from `.env` files using the `python-dotenv` library. See <<image_secrets_loading_architecture>> for the complete architecture.

[[image_secrets_loading_architecture]]
.Loading secrets from .env in development and from secret management systems in production
image::img/ch01_images/secrets_loading_architecture.png[Loading secrets from .env in development and from secret management systems in production]

[TIP]
====
Treat `.env` files as a local development convenience only. For production deployments, always use a managed secret store provided by your cloud platform.
====

This recipe uses the `python-dotenv` library to load secrets from a `.env` file into environment variables.

[source,bash]
----
pip install python-dotenv
----

Put each secret into your `.env` file using the format `KEY=VALUE`. Most SDKs expect specific environment variable names, so always check the documentation. For example, OpenAI looks for `OPENAI_API_KEY`.

[source,text]
----
HUGGINGFACEHUB_API_TOKEN=hf_...
OPENAI_API_KEY=sk-...
----

Make sure `.env` is listed in your `.gitignore`. This prevents Git from tracking it. When you create a new repository on GitHub, a default `.gitignore` is often generated for you. Add `.env` if it is not already included. The following snippet shows an example `.gitignore` file with common file types that are typically ignored.

[source,text]
----
# Environments
.env
.venv
.vscode
env/
venv/
----

To load secrets in your Python code, call `load_dotenv()` once at startup. You can then access values using `os.getenv()`, as shown in the following code snippet:

[source,python,indent=0]
----
from dotenv import load_dotenv
import os

load_dotenv()

openai_key = os.getenv("OPENAI_API_KEY")
----

==== Discussion

Environment variables are key-value pairs that your program reads from the operating system at runtime. They provide a standard interface for accessing configuration and secrets without hardcoding values in source code.

The `.env` approach works well for local development because it keeps secrets out of version control without requiring cloud infrastructure. However, `.env` files are plain text stored on disk, providing no encryption or access control.

For production systems, use managed secret stores like AWS Secrets Manager, Azure Key Vault, or HashiCorp Vault. These services provide encryption at rest and in transit, audit logging, automatic rotation, and fine-grained access controls. Most cloud platforms inject secrets directly as environment variables at runtime, so your application code remains unchanged—it still uses `os.getenv()`.

Don't share `.env` files via email, Slack, or shared drives when multiple team members need access to the same secrets—this defeats the security benefits. Instead, use a shared development secret store or credential management tool like 1Password or AWS Secrets Manager with developer access.

The key principle: secrets should never be hardcoded in source code or committed to version control. Whether you use `.env` locally or a managed service in production, environment variables provide a consistent interface for accessing secrets.

=== Building Your First RAG App

==== Problem

You want to get started and build your first RAG based conversational knowledge chatbot.

==== Solution

Every RAG system is built around three essential components:

1. An embedding model that represents text as vectors
2. A vector store that searches those vectors
3. An LLM that generates answers from retrieved context

Follow this workflow:

**Data Ingestion:**

1. Split documents into smaller chunks
2. Generate embeddings for each chunk
3. Store vectors in a vector database

**Query Processing:**

<<basic_rag_flow>> illustrates the complete RAG pipeline.

1. Convert the user's question into an embedding vector
2. Search the vector database for the closest matching vectors
3. Select the most relevant chunks
4. Send chunks together with the user's question to the LLM

In the last step, the LLM generates an answer using this context.

[[basic_rag_flow]]
.Basic RAG Pipeline Overview
image::img/ch01_images/basic_rag_flow.png[Basic RAG Flow]

Before you begin, make sure you have the following:

- OpenAI account and API key from https://platform.openai.com/signup[OpenAI Platform]
- ChromaDB for vector storage (for vector store concepts, see <<chapter_similarity_search>>)

This recipe demonstrates the workflow by building a Harry Potter knowledge chatbot. <<harry_potter_chatbot_architecture>> illustrates the overall architecture this recipe implements. The retriever searches a ChromaDB vector store built from the Harry Potter books, and the generator uses OpenAI models to answer questions based on retrieved context.

[[harry_potter_chatbot_architecture]]
.Harry Potter Chatbot RAG Architecture
image::img/ch01_images/harry_potter_chatbot_architecture.png[Harry Potter Chatbot RAG Architecture]

**Step 1: Text chunking**

This recipe builds RAG from scratch without frameworks to demonstrate how simple the core concepts are. RAG orchestration frameworks like LangChain and LlamaIndex provide ready-to-use chunking functions, but this example avoids those dependencies to keep the implementation lightweight and the core concepts clear.

The following code demonstrates how to chunk text at natural boundaries, such as paragraphs or sentences, with overlap to preserve context across chunks.

[source,python,indent=0]
----
from pathlib import Path
import chromadb
from openai import OpenAI


def chunk_text(text, size=1000, overlap=200):
    chunks, start = [], 0
    while start < len(text):
        end = min(start + size, len(text))
        if end < len(text):
            bp = text.rfind("\n\n", start, end)
            if bp == -1:
                bp = text.rfind(". ", start, end)
            if bp > start:
                end = bp + 1
        chunk = text[start:end].strip()
        if chunk:
            chunks.append(chunk)
        start = end - overlap if end < len(text) else end
    return chunks


file_path = Path("datasets/text_files/harry_potter.txt")
text = file_path.read_text(encoding="utf-8")
chunks = chunk_text(text)
----

**Step 2: Embed and store in ChromaDB**

If you run this cell multiple times and get ID conflicts, delete the `chroma_db` folder or use a new collection name.

[source,python,indent=0]
----
client = OpenAI()
embedding_model = "text-embedding-3-small"


def embed_and_store(chunks, db_path, collection_name):
    chroma = chromadb.PersistentClient(path=str(db_path))
    collection = chroma.get_or_create_collection(
        name=collection_name,
        metadata={"description": "Harry Potter knowledge base"},
    )

    embeddings = []
    for i in range(0, len(chunks), 100):
        batch = chunks[i : i + 100]
        res = client.embeddings.create(model=embedding_model, input=batch)
        embeddings.extend([x.embedding for x in res.data])

    collection.add(
        ids=[f"chunk_{i}" for i in range(len(chunks))],
        documents=chunks,
        embeddings=embeddings,
        metadatas=[{"chunk_index": i} for i in range(len(chunks))],
    )
    return collection


chroma_db_dir = Path("chroma_db")
collection = embed_and_store(chunks, chroma_db_dir, "harry_potter_kb")
----

**Step 3: Test retrieval**

With data stored, test that the retrieval system finds relevant chunks for a given question.

[source,python,indent=0]
----
def retrieve(question, top_k=3):
    q_emb = client.embeddings.create(
        model=embedding_model,
        input=question,
    ).data[0].embedding

    res = collection.query(
        query_embeddings=[q_emb],
        n_results=top_k,
        include=["documents"],
    )

    return res["documents"][0]


question = "Why did Uncle Vernon take the family to a hut in the middle of the sea?"
docs = retrieve(question)
----

**Step 4: Test generation**

Once retrieval works correctly, test the generation step. The following code feeds the retrieved documents and question to the LLM to generate an answer.

[source,python,indent=0]
----
def answer(question, docs):
    context = "\n\n---\n\n".join(docs)
    prompt = f"""Answer the question using only the context below.

Context:
{context}

Question:
{question}

Answer:"""

    res = client.chat.completions.create(
        model="gpt-5-mini",
        messages=[{"role": "user", "content": prompt}],
    )

    return res.choices[0].message.content


question = "Why did Uncle Vernon take the family to a hut in the middle of the sea?"
docs = retrieve(question)
answer_text = answer(question, docs)
----

With the retriever and generation working, you have a first basic RAG system.

==== Discussion

This basic RAG pattern works when your data fits in a single vector store and users ask direct factual questions. It fails when queries require multi-step reasoning ("compare X and Y, then recommend Z") or when different data types need different retrieval strategies. For example, combining structured database queries with document search requires orchestration beyond simple vector similarity.

Test retrieval independently before debugging generation. If the retriever returns irrelevant chunks, fix retrieval before adjusting prompts or LLM parameters. If answers feel generic or unrelated to your documents, the problem is usually retrieval quality, not the LLM.

As you progress through this book, you'll learn a variety of techniques for both retrieval and generation that can be combined to build more sophisticated RAG systems tailored to your specific use cases.

==== Discussion

Orchestration frameworks like LangChain, LangGraph, and LlamaIndex (from <<rag_libraries_table>>) provide pre-built components for common RAG tasks—retrieval chains, prompt templates, memory management, and agent loops. This accelerates development when building standard patterns. However, frameworks bundle many functions and pull in substantial dependencies. <<langchain_text_splitters_deptree>> shows the dependency tree for the `langchain-text-splitters` library.

[[langchain_text_splitters_deptree]]
.Example: Dependency tree for a framework component
image::img/ch01_images/langchain-text-splitters-deptree.svg[LangChain Dependency Tree]

Each dependency introduces potential breaking changes, version conflicts, security updates, and incompatibilities. Projects with 100+ dependencies (common with full framework adoption) require significantly more troubleshooting than those using 5-10 core libraries.

Use frameworks when building applications that need multiple RAG patterns—conversational memory, multi-step retrieval, tool calling, and re-ranking. Frameworks handle the integration work between these components. Don't use frameworks for simple applications that only need vector search and generation. A direct implementation with OpenAI and ChromaDB requires 2-3 dependencies instead of 50+.

Consider starting simple and adopting frameworks when complexity justifies the trade-off. You can migrate a basic retriever-generator implementation to a framework later if requirements expand. Going the opposite direction—simplifying from framework to direct implementation—is much harder.
